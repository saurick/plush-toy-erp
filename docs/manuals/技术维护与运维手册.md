# 技术维护与运维手册 / Engineering And Operations Handbook

本手册供开发、运维和后续接手人员使用，串联当前工程的开发、验证、发布、迁移、备份、恢复和排障主路径。业务办理见[业务使用手册](业务使用手册.md)，人员、权限和实施交接见[管理员与实施手册](管理员与实施手册.md)。

以下命令描述当前仓库入口，不代表已经在任何目标执行。先从当前 checkout 确认仓库根，目标、版本、凭据和环境配置按各自正式合同读取；不从历史回执推定当前运行状态。

可从“帮助中心 → 技术运维”在线阅读。书目与正文按账号权限开放，切换推荐岗位不扩大权限；打开“下载手册”后选择 HTML 或 Markdown，HTML 可离线查找并通过浏览器打印为 PDF。

## 架构与真源 / Architecture

服务端使用 Go、Kratos、Ent、Atlas 和 PostgreSQL，前端使用 React、Vite 和 Ant Design；Trace 使用现有 OpenTelemetry 接入。具体版本以 `server/go.mod`、`web/package.json`、锁文件及配置为准，不把本文数字当作依赖锁。

| 层 | 负责 | 实际入口 |
| --- | --- | --- |
| HTTP / JSON-RPC | 接入、方法分发、DTO 与入口鉴权 | `server/internal/server`、`server/internal/service` |
| 领域 | 状态、权限、事务意图、幂等与业务规则 | `server/internal/biz` |
| 数据 | Ent、SQL、外部服务与领域 repository | `server/internal/data` |
| 数据结构 | Schema、生成 Ent 与版本化 Atlas migration | `server/internal/data/model` |
| API / UI | 展示、交互、请求生命周期与反馈 | `web/src/erp`、`web/src/common` |
| 开发工作台 | 只在开发环境使用的文档、设计、验证与受控运维入口 | `web/src/dev-workbench`、`web/dev-server` |

MasterData、Source Document、Workflow、ProcessRuntime、Fact / Ledger 和控制面审计分别核对。Workflow task done 不能表示库存、检验、出货或财务已过账；Workflow 不直接写领域事实。

后端代码、正式 schema、migration 和测试核对实现；正式 docs 描述合同；progress、archive 和历史回执只证明当时事实。入口见[当前真源与交接顺序](../当前真源与交接顺序.md)。

## 首次接手与定位 / Taking Over

1. 从当前 checkout 确认仓库根、HEAD 和工作区差异，识别他人未提交内容，保留 index 与现有运行服务。只读 Git 查询设置 `GIT_OPTIONAL_LOCKS=0`，diff 同时使用 `-c diff.autoRefreshIndex=false`。
2. 先确定问题在业务 UI、开发工作台、后端、数据库、附件还是发布目标。前端入口读 `web/README.md`，后端入口读 `server/README.md`，目标登记读部署合同，不先改运行配置。
3. 记录待核验的来源单号、动作、实际结果及请求时间；如需日志，关联同一 request / trace。截图和旧回执不能替代当前版本读回。
4. 若只改帮助或文档，使用生成、契约和相关浏览器检查；不为文档变更启动数据库迁移、真实导入或目标发布。

| 维护对象 | 从哪里定位 | 连带核对 |
| --- | --- | --- |
| 业务字段和动作 | `web/src/erp/pages`、对应 `components`、`server/internal/biz` 与 `data` | DTO、公共契约、来源切换 / 清空、状态与权限、打印导出 |
| 资料表单 | `web/src/erp/components/master-data` | 产品 / SKU、材料单位、交易条件、图像附件和历史快照 |
| 业务帮助与手册 | `businessUsabilityCatalog.mjs`、`businessHandbookOperations.mjs`、`businessHandbook.mjs` | 搜索、完整词条深链、在线章节、Markdown、离线 HTML 和 PDF |
| 岗位与流程 | 角色入口、Workflow / ProcessRuntime 专题及实际 usecase | 任务责任、业务结果、审批冻结与执行分别核对 |
| 目标运行问题 | 目标 registry、正式 operation、当前 manifest 与读回 | SHA、image、config、migration、health / ready、真实业务结果 |

## 环境与依赖 / Environment

在仓库根执行只读环境检查：

```bash
bash scripts/doctor.sh
```

按输出及 `server/go.mod`、`web/package.json` 安装匹配的 Go、Node.js、pnpm 和项目依赖。后端 Go toolchain 在 `server/` 模块内确认，避免误用仓库根的默认 Go。

本地开发端口与后端身份使用 `config/dev-ports.env` 和受控运行入口；不要凭某个监听端口或标签标题认定服务归属。真实凭据保留 ignored 的受保护本机配置，不进入 Git、手册、日志或导出包。

## 本地启动与重启 / Local Development

### 首次和日常启动

1. 确认当前 checkout、依赖、数据库角色与附件配置。首次角色准备使用服务端正式入口，详见[后端快速开始](../../server/README.md#快速开始)。
2. 从 `web/` 启动统一前端入口，终端输出的实际 URL 为准：

   ```bash
   pnpm start
   ```

3. 启动会先核对当前工作区迁移、数据库及后端状态；条件满足时按正式后端链路构建并验证。不要跳过失败预检或让启动自动 apply migration。
4. 前端加载当前 Vite 源码并热更新。后端代码修改后，从 `server/` 使用 `make dev_restart` 按需编译、切换和验证。
5. 数据库预检失败时业务保持阻断，恢复入口 `/__dev/database-migration` 仍可达。恢复后回原页面核对；不重放结果不确定的业务写入。

### 常用只读和受控入口

| 工作目录 | 命令 | 行为 |
| --- | --- | --- |
| `server/` | `make dev_status` | 只读核对进程、版本、源码一致性、预检和当前操作 |
| `server/` | `make dev_logs` | 查看已有服务日志，不启动、不构建、不迁移 |
| `server/` | `make run` | 确保本工作区服务运行；不把旧源码版本称为最新 |
| `server/` | `make dev_restart` | 预检、按需构建、切换和验证当前工作区 |
| `server/` | `make dev_rebuild` | 强制构建候选，再受控切换 |
| `server/` | `make dev_stop` | 核对归属后停止登记后端 |
| `web/` | `pnpm start:isolated` | 为独立前端验证选择辅助端口 |
| `web/` | `pnpm start:yoyoosun --print-plan` | 读取当前客户开发入口计划，不把静态预览当作开发源码 |

预检或编译失败保留旧进程，但新代码没有生效。只有最终 `started ... health=passed ready=passed business=passed` 表示本次后端切换成功。取消日志查看不停止独立后端。运行与恢复细则见[后端 README](../../server/README.md)和[前端 README](../../web/README.md)。

## API、权限与字段 / Contracts

JSON-RPC 入口、域、method 和请求合同见 [API 文档](../../server/docs/api.md)。跨层状态、权限码、RPC 标识、附件与数值约束复用[公共契约与生成规范](../engineering/跨层公共契约与生成规范.md)，不要在页面再造业务判断。

1. 先确定字段的权威来源、来源单据快照和正式缺值规则，再修改 DTO、usecase、repository 及前端映射。
2. 覆盖新建、编辑、来源切换与清空、缺失值、冻结资料和相关打印 / 导出 / 搜索，避免旧值残留或前端补造事实。
3. 写操作通过受控 Go usecase / repository；校验有效账号、来源读取、RBAC、责任、数据范围、状态、版本和幂等。
4. 客户差异优先使用已有配置消费者，不能以页面分支提升权限或越过领域状态机。
5. 请求切换、取消与旧响应要正确处理；业务错误使用统一文案与错误码，不把原始错误、栈或内部标识透传给员工。

数据库字段说明见[数据字典](../../server/docs/database/README.md)，数量和金额口径见[业务公式](../product/业务公式与计算口径.md)。

## Schema 与迁移 / Database Changes

Schema 修改后从 `server/` 生成，检查全部产物：

```bash
make data
```

收口前在仓库根及 `server/` 分别运行适用检查：

```bash
# 仓库根
bash scripts/qa/db-guard.sh

# server/
make migrate_check
make migrate_status
make migrate_audit
```

`make data` 生成 Ent、Atlas migration 和 `atlas.sum`，不修改开发库；不能改写已执行 migration。生成物或版本化 migration 缺失时结构变更未完成。

涉及存量转换时，把现库备份恢复到隔离库，验证已过账事实、冻结快照、历史缺值、升级结果和 seed / fixture。空库成功不能替代现库存量升级。

### 登记共享开发库

1. 使用迁移页或 `server/` 的 `make migrate` 进入正式准备链路。
2. 非交互环境先运行 `make migrate_prepare`；ready 输出只证明准备成功、尚未正式写入。
3. 核对同次操作绑定的目标、候选、迁移、备份和恢复证据，取得真实 apply 授权后，按该 ready 输出的 operation / confirm 执行 `make migrate_execute`。
4. 检查实际 apply、数据库读回和后端切换结果；缺任一层不能称为迁移完成。

隔离库使用对应生命周期，测试、生产或归属不明的数据库使用正式目标流程。禁止直接 SQL 绕过、revision 标记跳过失败或启动自动迁移。合同见[Ent 与 Atlas](../../server/docs/ent.md)及[脚本入口](../../scripts/README.md)。

## 验证与构建 / Validation

按实际改动选最小充分检查，使用受控只读 Git 环境：

```bash
# 仓库根：只查看影响计划
GIT_OPTIONAL_LOCKS=0 bash scripts/qa/affected.sh --plan

# web/：前端静态、样式和同名测试按改动选择
GIT_OPTIONAL_LOCKS=0 pnpm lint
GIT_OPTIONAL_LOCKS=0 pnpm css
GIT_OPTIONAL_LOCKS=0 pnpm test

# web/：只运行选定浏览器场景
GIT_OPTIONAL_LOCKS=0 STYLE_L1_SCENARIOS=<当前场景名> pnpm style:l1
```

`<当前场景名>` 从当前 `web/scripts/style-l1` registry 选择并替换，不原样执行。数据库、权限、事务、并发、页面、移动端及打印分别使用对应验证；同一层绿色不能替代其他层。

正式 full / strict、exact-SHA CI 和发布合同见[自动化测试策略](../product/自动化测试策略.md)、[QA 入口](../../scripts/qa/README.md)与[发布门禁](../product/发布门禁.md)。单测和本地构建不等于目标发布或客户验收。

### 按改动验证的具体选择

| 改动 | 需要证明 | 不能替代的证据 |
| --- | --- | --- |
| 帮助、手册及布局 | 来源无漂移、搜索命中新增说明、词条深链、宽窄屏导航与可读性、离线内容一致 | 业务写入、目标部署与客户培训验收 |
| 表单带值和清空 | 新建、编辑、来源切换 / 清空、缺值和旧快照，不留残值 | 只检查保存按钮或单个成功截图 |
| 审批或财务动作 | 后端权限、责任分离、状态、幂等、实际确认、余额与反向记录 | Workflow done、HTTP 200 或前端按钮隐藏 |
| Schema 与迁移 | 生成、迁移序列、存量隔离升级、审计与 seed 仍合法 | 空库建表成功、未执行的准备结果 |
| 发布 / 恢复 | 同一固定制品、目标读回、备份和恢复点、选定业务及附件 smoke | 本地绿色或历史健康回执 |

## 不可变发布与目标操作 / Release

当前生产 Compose 唯一真源为 `server/deploy/compose/prod`，目标登记读取 `scripts/deploy/deployment-targets.json`。目标机只加载或拉取制品、迁移、启动和检查，不临时构建源码；DEV 工作台和模拟记录不进入生产能力证明。

1. 固定已提交产品 SHA、版本、image digest、迁移序列、客户配置身份和回滚点；核对当前 target registry，不从旧手册推定某个目标仍可写。
2. 按 canonical GitLab pipeline 完成 exact-SHA 质量门禁，并构建同一 SHA 的不可变制品。
3. 用同一制品 bytes 完成隔离 release rehearsal，校验 manifest、SBOM、checksums、镜像和对应恢复证据。当前发布资格要求见[部署脚本](../../scripts/deploy/README.md)。
4. 目标执行前做即时只读 preflight，核对容量、当前运行身份、Compose、配置、迁移、备份和 rollback point。
5. 通过正式 promotion controller 创建具体 ready operation，按已确认的单一 target 执行；不拼接临时 SSH、shell 或 SQL 绕过执行器。
6. 完成后分别读回 Compose、容器镜像、发布身份、health、ready、登录、配置、权限和业务 smoke，保存本次脱敏回执。

main push 不自动部署。运行中断或结果为 not_proven 时先核对目标现状，不自动重试。操作记录与 GitLab 远端活动分别读取，不伪造 operation。

## 数据库与附件备份 / Backup

完整系统备份包含同一停写窗口的 PostgreSQL custom-format dump、配套附件对象、必要配置身份及 release / migration 信息。密钥本身通过受保护的凭据管理保存，不写进公开清单。

附件的元数据和对象 key 在 PG，文件内容使用统一 S3 接口。现有仅 PostgreSQL 定时备份不能证明外置附件已备份；RAID、镜像或运行中对象目录打包也不能替代完整恢复验证。

1. 核对目标与备份范围，按正式入口停止相关写入。
2. 在同一窗口生成 PG dump 和附件文件备份，记录 hash、release、migration 和对象完整性。
3. 把备份保存在独立磁盘、机器或受控远端，并保留项目要求的回滚版本。
4. 在隔离环境恢复配套 PG dump，再使用独立 S3 endpoint / bucket 恢复并验证对象。
5. 核对原 key、附件 ID、hash、关键数量金额、权限及业务只读 smoke，保存本次证据。

受控附件命令、确认参数、存储模式和独立验证入口见[附件存储与恢复](../../server/deploy/compose/prod/README.md#附件存储与raid5)。本手册不复制会漂移的凭据、目录或一次性确认串。

## 回滚、恢复与清理 / Rollback And Recovery

代码回滚只使用 migration 序列及配置身份兼容的旧 manifest，不自动 down migration，不自动恢复数据库。配置 rollback、应用 rollback、数据恢复和基础服务回退是不同操作。

1. 先核对当前运行版本、实际数据库及原 rollback point，保留失败日志与现场。
2. 能使用兼容旧应用时走正式 rollback controller / executor；不兼容时评审 forward-fix 或配套数据恢复。
3. 数据恢复先在隔离目标演练，核对 PG 与附件一致性，确认后才切换业务连接。
4. 恢复后重新检查 health、ready、登录、权限、配置与选定业务结果；旧环境或空报告不能代替本次读回。
5. 回滚窗口结束前保留源对象、旧备份和规定版本。清理只删除归属明确、已过期且可重建的制品，不做 volume prune，不删数据库、上传、配置、证书或运行依赖。

## 日志、Trace 与故障定位 / Diagnostics

服务端每次请求记录完成摘要，包含 operation、RPC 标识、request / trace、transport code、业务结果、outcome 和耗时。成功、业务拒绝与系统失败分别分类；HTTP 200 不能证明 JSON-RPC 业务成功。

| 问题 | 定位顺序 | 恢复核对 |
| --- | --- | --- |
| 页面或登录不可用 | 当前入口 → 后端身份 → health / ready → 数据库预检 | 原 URL 恢复、当前代码已生效、无重放写入 |
| 业务动作失败 | 来源与状态 → 有效权限 → 同一 request / trace → 领域拒绝 | 对应正式记录和任务结果，无重复办理 |
| migration 阻断 | 工作区版本 → Atlas 状态 → 存量审计 → 同次准备证据 | 实际 apply 和读回完成，不跳过 revision |
| 附件不可用 | PG 关联 → S3 endpoint / bucket → 对象 hash → 服务状态 | 列表、预览下载及恢复对象一致 |
| PDF 不可用 | 当前单据和模板 → PDF runtime / Chromium → 字体与附件 | 同版本输出、分页和缺值提示正确 |
| 发布结果不确定 | operation → 目标运行 SHA / 镜像 → 公网入口 → 回滚点 | 只读核对后再决定重试或回滚 |

技术日志与 Trace 用于定位，Trace 可能采样或缺失。业务审计分别使用 Source、Workflow、ProcessRuntime、Fact / Ledger 和控制面记录，不能把技术日志当作业务账本。

日志不得记录密码、完整 token、密钥、RPC 参数或无必要 PII。临时增加日志级别时保持脱敏与范围，完成后回到正常配置。详细入口见[观测规范](../observability/日志链路追踪与审计.md)和[集中日志运维](../observability/集中日志接入与运维.md)。

### 企业补充与纠错维护

正式手册仍从上述共享配置与 Markdown 生成，后端嵌入的 `documents.generated.json` 同源记录章节身份、来源 hash、岗位和页面阅读边界。运行中的编辑功能只写企业补充，不提供仓库文件编辑或任意文件读写。

`help_supplements` 保存章节草稿与发布指向，`help_supplement_revisions` 保存每次保存、发布和恢复的完整不可变记录，`help_feedbacks` 保存员工纠错和维护回复。写入由 Go usecase / repository 执行；版本检查、状态更新和修订追加处于同一事务，修订追加失败必须整体回滚。正文与纠错不写入技术日志，操作日志沿现有请求链记录动作、操作者和章节。

六项 `help.*.edit / publish` 权限按三册分开，仍须先具备章节阅读权；普通岗位默认不授予这些能力。反馈只允许当前有效账号提交，读者只能读取本人反馈，维护者可读取对应手册的可读章节反馈。接口不接受调用方指定的账号、岗位或文件路径。

发布记录是在线正文、搜索和在线下载的共同来源，草稿不进入普通阅读接口。历史恢复先创建新草稿，发布后生效；清空正文并发布撤下当前补充。数据库备份必须包含以上三张表，恢复后核对已发布指向、历史记录及纠错回复。仓库离线产品手册包不包含部署中的企业资料。

## 完成与交接 / Closeout

交接记录说明修改路径、当前版本、实际验证、盲区、尚未执行的迁移 / 发布、运行与回滚身份及必要下一步。Git 提交、推送和部署各自授权，不因手册生成或测试通过自动执行。

当前产品是单客户私有化 Product Core；没有任意插件执行器、自由状态机编排、SaaS tenant、license 或计费服务。新增这些能力须另行评审；现有文档、原型和配置候选不能作为实现证据。
