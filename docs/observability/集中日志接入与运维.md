# 集中日志接入与运维 / Centralized Logs

项目使用 Alloy、单实例 Loki 与 Grafana 收集技术日志。业务服务继续写原有日志，不依赖观测服务的可用性；业务审计和事实仍保存在各领域权威对象中。配置真源位于 `server/deploy/compose/prod/compose.observability.yml` 和相邻 `observability/`，本地入口为 `node scripts/observability.mjs`。

本文面向开发与运维。该入口启动当前工作区的独立观测 Compose project，不更新业务应用、数据库或客户配置，不代表新的产品 release 已发布。正式业务版本继续走 [部署约定](../部署约定.md)。

公网与内网 DNS 均为 DNS-only A，沿用已有泛域名证书；LAN 域名已加入现有证书同步探测。Home Nav 的健康状态以公网 HTTPS 为准，保留原有容器到 LAN 的隔离。具体转发、防护、证书同步与精确恢复由服务器 `/srv/host-control/HTTPS.md` 和堆栈 `README.md` 定位。

## 采集范围 / Sources

| 环境 | 来源 | 边界 |
| --- | --- | --- |
| `local-dev` | 当前工作区 `output/dev-workbench/database-migration-runtime/` 的 UUID 后端日志；`output/dev-workbench/web-logs/vite-<port>.log`；登记的开发 PostgreSQL、Jaeger | 后端重启的新文件自动发现；主前端和客户前端通过同一启动 helper 保存日志。浏览器异常通过已登录会话的 RPC 进入后端日志 |
| registry 登记的部署 target | 固定 project 的 server、web-desktop、PostgreSQL、Jaeger，对应受控 public Web 容器与登记的 Web FRPC | 用 `--include-targets` 显式开启，业务容器与环境来自 `scripts/deploy/deployment-targets.json`；核对本机 hostname、用户和 IPv4 与 registry 一致后只读采集 |
| `shared-infra` | 登记的 SeaweedFS 容器 | 共享附件服务只归入此环境一次，按请求编号关联业务环境；不复制到每个客户环境 |

补充来源真源是 `observability/sources.json`，绑定宿主机名称与精确容器名。当前登记 `r740xd` 的 `development-postgres-133`、`development-jaeger-133`、`seaweedfs` 及两条 ERP Web FRPC；其他主机不会自动采集这些名称。新增独立依赖须修改这份清单并重新准备配置，不使用全宿主机容器通配采集。

Docker 接口由独立 socket proxy 提供，只开放 GET/HEAD 所需接口，关闭写入与启停能力，不发布宿主端口。采集配置在 discovery 与 relabel 两处收窄容器范围。该只读接口仍属于运维权限，能读取容器元数据，不能开放给业务账号或外部网络。

本地文件只挂载两个指定日志目录。Alloy 使用当前开发用户的 UID 和固定镜像状态目录的 473 group，原始日志保持 owner 私有权限，无需把后端日志改为共享可读。

环境、服务、主机、级别和 stdout/stderr 是索引标签；请求、Trace、任务与业务对象 ID 保留在日志内容中。日志不新增请求体、响应体、SQL 参数、密码、token 或客户原件。数据库仍关闭完整语句与参数记录。

## 日志合同与浏览器上报 / Event Contract

| 来源 | 可检索字段与行为 | 统计口径 |
| --- | --- | --- |
| JSON-RPC | 每次完成一条摘要；包括正常响应、请求取消、业务拒绝、解码前的 400/413 和 panic。`request_id`、`rpc.service`、`rpc.method`、结果码、耗时；已认证请求附 `actor_id`，解码前失败只保留安全路由 | `outcome=success/canceled/rejected/error`；请求上下文已取消且错误链仅为 `context.Canceled` 时返回 `49900`，完成摘要为 INFO / canceled；其他 HTTP 4xx（包括权限拒绝、限流）为 rejected，HTTP 5xx / 内部错误为 error。日志、RPC 错误计数和 Trace 共用分类，健康探针与普通 HTTP 不进入 RPC 计数 |
| 关键业务动作 | 采购收货、库存操作、财务过账/结算/冲销、真实出货附 `business_object_kind`、`business_object_id`；任务处理与催办复用 `task.id` | 记录经过校验的关联标识，不记录 DTO 内容，不代替业务事实与审计 |
| 自定义 HTTP / 后台任务 | HTTP 4xx 为拒绝、5xx 与后台实际失败为错误；就绪探针只在依赖状态改变时产生生产级别事件 | `outcome` 表示事件结果；持续故障下的探针轮询不逐次放大告警 |
| Web 反向代理 | 校验或生成 `X-Request-Id` 并透传；失败只记录一次，保留安全路由、status、原因类别和耗时 | 不记录完整 URL、查询参数或原始 upstream error |
| S3 | `dependency=attachment_s3`、operation、固定 reason、耗时和请求编号；保留原有 unavailable 错误合同 | `dependency_outcome=error` 独立统计，不将每层诊断重复当作请求失败；不记录对象 key、上游响应正文或凭据 |
| 浏览器 | runtime、未处理 Promise rejection、React 错误边界；构建号、安全页面路径、异常类别、最多五个代码位置和 fingerprint | 有效登录会话才上报；匿名和 mock 不采集。单页面每分钟最多十条且去重，后端全局每秒两条、突发二十条；无排队和重试 |

浏览器上报复用 `auth/report_client_error` 和既有 session 校验，不增加表或外部异常平台。消息、完整 stack、来源主机、URL query、业务路径中的未知标识及表单数据不进入报告；只保留 `/assets/` 或 `/src/` 中的受限代码位置。上报失败不阻断页面，也不重复上报已由服务端记录的 `RpcError`。

Web 代理与后端 HTTP 入口只沿用 1–128 个 ASCII 字母、数字或 `._:-` 组成的 `X-Request-Id`；缺失或非法时生成新编号，并将同一编号用于请求头、上下文、响应头和日志。请求完成摘要中的 RPC 名称和 ID 也限制格式与长度，结构化名称与 Trace 使用同一规范化规则。

浏览器 `JsonRpc` 把响应头中的合法编号保存到 `RpcError.requestId`，覆盖 HTTP、框架、业务、JSON 解析和响应合同错误；它只供排障使用，不拼进用户错误文案。未收到响应、缺失或非法的编号保持 `null`，不伪造服务端关联。

非终端 logger 将整条 JSON 与换行原子写入，错误对象取诊断文本而不序列化私有字段；字符串字段及 `Errorf/Warnf` 等格式化消息使用同一凭据脱敏，覆盖带凭据的 URL、Bearer 和常见密码 / token 赋值。脱敏只是保护层，调用方仍须省略请求体与 PII。Panic 只保存类型和有界运行栈，不保存 panic 值或完整请求。

以上为代码观测合同，不表示每个用户动作都形成完整 Trace 或线上日志已经可查询。浏览器仍只有有效登录会话的异常上报；离线且没有服务端响应的请求没有服务端编号。后台对账依靠批次 Trace 和 task / process / node ID，不冒充 HTTP 请求。目标采集、日志读回、Trace 保留及告警送达须分别验证。

以下命令从当前 checkout 根目录执行；容器运行时和当前项目 Node 工具链须可用。

1. 预置 Compose 中固定的四个第三方镜像，使用文件内完整 tag 和 digest；不使用 `latest`，不构建业务镜像。

   ```bash
   docker pull grafana/alloy:v1.20.1@sha256:2aa2099af76c0098d4af7a4d6e48f86cb66dc1a000222ad927a1c67c6542d13f
   docker pull grafana/grafana:13.2.3@sha256:b28bae15e219c998fb0e0424ed724930cc61b1f61fb404d47c862f9a23f9e572
   docker pull tecnativa/docker-socket-proxy:v0.5.0@sha256:1f5038b54f06c3e18422902cf00ba21803d1c97805aae032e5e6673d532d3459
   ```

2. 准备并启动工作台。首次默认采集当前工作区的本地日志与该主机登记的本地/共享依赖，Grafana 绑定 `127.0.0.1:3130`。已有运行实例保留此前启用的部署 target 范围。

   ```bash
   node scripts/observability.mjs --start
   ```

   同机已运行登记的 ERP 部署目标时，可追加容器采集；需要从个人内网浏览器访问时，显式指定本机私网 IPv4：

   ```bash
   node scripts/observability.mjs --start --include-targets --bind-address 192.168.0.133
   ```

   脚本检查镜像与配置，应用配置并重建观测容器，保留持久化数据；Loki、Alloy 就绪与组件健康、Grafana 的 HTTP 检查全部通过后才报告成功。失败保留本套现场供诊断，不自动重试或重启业务容器。

3. 以终端输出的 Grafana 地址登录，打开“ERP observability → ERP 日志排查”。初始管理员用户名和随机密码在当前工作区 `output/dev-workbench/observability/.env`，权限为 `0600`；命令输出不显示密码。注册和匿名访问关闭，未配置反向代理时仅用于受控本机或个人内网。

4. 按正式开发入口启动或重启本地服务，Vite 日志副本从这次启动开始生成。已有后端日志可以直接采集。

   ```bash
   cd web
   pnpm start --local --restart
   pnpm restart:yoyoosun
   ```

   后端代码变化仍按 `server/README.md` 使用正式 `make dev_restart`；观测服务不会替开发服务执行构建、迁移或重启。

## 查询与告警 / Query And Alerts

仪表盘按环境、服务、时间和请求编号或关键字查询；系统错误事件、业务拒绝、依赖失败和未归类 ERROR 日志分别计数。数值是相应事件或日志条数，不能将多层诊断直接相加作为失败请求数。没有日志的环境不会产生数据，不能把空结果当成采集中断。

请求过滤框为空时显示所选服务的全部日志，中文和双引号可直接输入。过滤采用 LogQL 双引号字符串；搜索路径中的一个反斜杠时输入两个反斜杠，例如搜索 `C:\logs` 时输入 `C:\\logs`。

本地历史文件首次读取采用采集时间，原始 `ts` 保留在 JSON 中；Docker 日志保留 Docker 来源时间。多行堆栈最多合并 128 行，单条等待最多 2 秒。正常业务日志仍保留原始正文。

每个环境使用对应的 Loki 查询入口。准备时只有读回正在运行的 Jaeger 容器及其网络，才配置该环境的 Trace 数据源，并仅把新 Grafana 容器连接到相应网络。仅已采样请求的 `trace_link_id` 有可跳转的值；超过 Trace 保留期后，历史日志中的链接可能查不到链路。环境查询入口方便筛选，不构成业务租户或不同客户的权限隔离。

固定版本的 Grafana 原生 Jaeger 插件通过 `jaegerEnableGrpcEndpoint` 开关使用 Jaeger v3 HTTP gateway，支持数据源健康检查、服务列表与按 Trace ID 读取，日志跳转复用这一查询路径。`--start` 会在服务就绪后检查所有已配置 Trace 数据源的插件健康响应，连接到 HTTP 服务本身不足以通过检查。

当前固定插件的条件搜索仍使用旧接口；按服务、耗时或标签搜索暂用对应环境的 Jaeger 原生 UI，通过现有 loopback / SSH tunnel 访问。

看板环境选项从本次准备的采集范围生成，包括 `local-dev` 和当前宿主机登记的共享依赖环境，启用 `--include-targets` 后追加 registry 中已启用的环境。运行看板位于 `output/dev-workbench/observability/dashboards/erp-logs.json`，源模板保持在 `observability/dashboards/`。环境选项不查询当前时间窗口的日志标签，因此没有新日志时仍保留选择与数据源。

看板默认查询最近二十四小时，顶部日志数按所选环境、服务和时间统计原始记录，不受关键字筛选影响。日志数为 0 或明细显示 `No data` 只表示该筛选与时段没有记录，可扩大时间范围；错误图只对同一个五分钟窗口内有日志的服务补 0，表示没有匹配错误，不为没有日志的服务补造健康结果。数据源查询失败仍单独显示错误。

判断采集健康须结合 `--status`、Alloy 组件与写入指标，必要时用只读业务请求及其 `request_id` 验证日志读回，不能用空闲时段的日志量代替健康检查。

当前页面的实际查询时间以右上角为准：URL 中的 `from/to` 会覆盖看板默认值，已打开的十五分钟窗口不会随默认值更新。顶部“查看最近 24 小时”和“查看最近 15 分钟”入口会明确切换时间，同时保留环境、服务和关键字筛选。排查本地开发请求须选 `local-dev`；`demo-133` 对应演示部署，`customer-test-133` 对应客户测试部署，各环境日志分别查询。

初始三条规则分别检测 `outcome=error`、`dependency_outcome=error` 和没有前两项结果字段的 ERROR/FATAL 日志；最后一类排除已由完成记录计数的 panic 栈。同一环境和服务五分钟内出现至少三条相应记录，持续两分钟后告警。无数据为正常，查询执行失败保留 Error 状态。`canceled` 和 `rejected` 不计入系统错误；HTTP 200 内的 JSON-RPC 系统失败同时进入日志和服务端错误计数。

请求取消只描述技术请求中断，不表示业务写入已回滚或已成功；写操作仍须读回正式业务对象。未取消的请求遇到依赖取消、超时、包含其他故障的混合错误链，继续按系统错误处理。公共 Web 将明确的客户端断连记录为 INFO / `canceled`，上游响应中断、依赖超时和真实 5xx 保持错误分类。PDF 后台预热接住已识别的字体准备失败，主动预览 / 导出仍保留失败提示；未知编程异常继续进入浏览器错误上报。

系统错误与拒绝规则依赖业务服务输出结构化 `outcome`；未归类 ERROR 规则补充已有 JSON 错误日志，但不能恢复旧版本遗漏的事件。接入采集不会升级已部署的业务版本；新日志合同须随正式业务发布生效。原始日志中的既有敏感信息也不会被采集接入自动修正；不要为此增加请求体记录。

首次配置保留告警评估并静默全部外发通知；通知政策和静默窗口由脚本生成。邮件设置保存在当前运行目录的 `.env`，准备脚本保留并校验这些设置；仅在 UI 修改受管配置会在下一次准备时被覆盖。主机与容器资源继续复用现有监控，不增加新的 Prometheus 或自建后台检查器。

邮件接入使用以下配置，不将真实地址或授权码写入仓库：

| 配置 | 用途 |
| --- | --- |
| `GRAFANA_SMTP_ENABLED` | 默认 `false`；配置完成后设为 `true`，允许发信和联系点测试 |
| `GRAFANA_SMTP_HOST` | SMTP 主机及端口，只接受隐式 TLS `465` 或强制 STARTTLS `587`，始终校验证书 |
| `GRAFANA_SMTP_USER` / `GRAFANA_SMTP_FROM_ADDRESS` | 发信登录账号与发信地址 |
| `GRAFANA_ALERT_EMAIL_TO` | 一个明确的收件邮箱 |
| `GRAFANA_ALERT_EMAIL_ENABLED` | 默认 `false`，保留全天静默；确认渠道和收件人并验证后设为 `true`，启用故障及恢复通知 |
| 运行目录 `smtp-password` | SMTP 授权码，仅由 Grafana 只读挂载；不进入 `.env`、Compose、provisioning 或验证报告 |

1. 在 `.env` 配置 SMTP 与收件人，保留 `GRAFANA_ALERT_EMAIL_ENABLED=false`；将授权码写入同目录的 `smtp-password` 普通文件。运行目录固定为 `0700`，文件为 `0644`，使容器内 Grafana 的独立 UID 可以读取，同时宿主机其他用户无法穿越父目录。准备脚本拒绝缺失、空白和符号链接凭据，不覆盖已有授权码。
2. 执行 `node scripts/observability.mjs --prepare`，检查生成配置。使用同一运行入口的 Compose 仅重建 `grafana` 服务（`up -d --no-deps --force-recreate --pull never grafana`）；邮件设置不要求重建 Loki、Alloy 或业务服务。
3. 在 Grafana 的 `plush-email` 联系点发送明确的测试通知，并核对 SMTP 接受结果和收件箱。测试联系点会实际发信，不受通知策略的静默窗口控制。
4. 将 `GRAFANA_ALERT_EMAIL_ENABLED=true` 写回 `.env`，再次准备配置，并通过 Grafana Admin API `POST /api/admin/provisioning/alerting/reload` 重新加载。用独立合成环境验证规则触发、邮件发送、恢复和恢复通知；SMTP 接受不等于收件箱送达。恢复静默时改回 `false` 后按相同方式重新加载。

Grafana 的文件凭据入口与 SMTP TLS 配置沿用[官方 Docker 配置](https://grafana.com/docs/grafana/latest/setup-grafana/configure-docker/)及 [SMTP 配置](https://grafana.com/docs/grafana/latest/setup-grafana/configure-grafana/#smtp)。

联系点与策略由文件管理，变更后须[重新加载 provisioning](https://grafana.com/docs/grafana/latest/alerting/set-up/provision-alerting-resources/file-provisioning/)。

Alloy 的 Docker healthcheck 每二十秒检查 `/-/ready`、`/-/healthy`、Loki `/ready` 和 socket proxy `/_ping`，三次失败后标为 unhealthy。健康脚本只依赖固定镜像已有的 Bash，不通过日志量判断故障。

133 的 Beszel 已有独立 `ContainerHealth` 规则与通知接收设置，持续十分钟不健康才进入告警；这条路径不依赖 Loki/Grafana。容器被停止或删除须另配 Beszel TCP monitor `127.0.0.1:12346`，现有健康规则不保证发现消失的容器；网络监控基于一小时丢包窗口，不能描述为即时故障/恢复。告警送达需独立验证，健康检查通过不证明通知成功。

## 容量、保留与恢复 / Retention And Recovery

| 项目 | 初始值 | 含义 |
| --- | --- | --- |
| Loki / Alloy / Grafana / socket proxy 内存上限 | 512 / 256 / 512 / 64 MiB | 是容器预算，不是实测占用或容量保证；Grafana 使用 512 MiB 为查询和插件保留空间 |
| Loki 保留期 | `168h` | TSDB 每日索引，compactor 每十分钟处理，删除延迟两小时；保留期不是硬磁盘配额 |
| 部署 Jaeger Trace 保留期 | `168h` | 业务 Compose 使用各 project 独立的 `jaeger-data` volume 和 Badger；须随正式 release 加载配置，旧内存存储的历史 Trace 不会迁入新 volume |
| 部署业务 / 后台根 Trace 采样 | `10%` / 至多 `10%` | 保留父链路决定；无父上下文的健康探针和无操作上下文的 SQL 不导出，错误日志与审计不跟随采样 |
| 部署 Jaeger 内存预算 | 容器 `192 MiB`，Go `128 MiB` | 接收端 memory limiter 为 `160 MiB`，spike 为 `32 MiB`，批次为 `256 / 512`；预算与反压不能代替目标负载验证 |
| Loki 接收限制 | 1 MiB/s，突发 2 MiB，最多 1000 streams | 超限会拒绝或限流，采集端有有限重试 |
| Alloy WAL | 最长 segment age `30m` | 持久化到本套独立 volume；超过范围或源日志已轮转，可能丢失；不承诺 exactly-once |
| Alloy 写入 | 256 KiB batch，有限 24 次重试 | 使用稳定版默认队列，不启用 experimental 配置；重试、丢弃指标可从 Alloy `/metrics` 核对 |
| 观测容器自身日志 | 每容器 10 MiB × 3 | 不把观测日志递归送回同一 Loki |
| 公共 Web 容器日志 | 每容器 10 MiB × 3 | 正式切换脚本为候选与公共容器显式配置；已有容器需正常切换/重建后才生效，不修改 Docker 全局默认值 |
| Vite 文件副本 | 每端口 10 MiB × 3 | 当前文件和两份轮转文件；写入失败只提示一次，终端输出继续 |

Grafana 使用 Go 原生 `GOMEMLIMIT=256MiB` 控制堆内存目标，512 MiB 容器上限同时覆盖进程、插件与缓存；该目标不等于宿主机总占用上限。

Trace 磁盘增长取决于采样后的 span 数、每个 span 的编码体积和索引开销。7 天 TTL 限制可查询跨度，过期空间由 Badger 后续清理回收，不能当作硬磁盘配额。调低保留期只影响技术观测数据；业务数据库事实、审计与备份保持各自保留合同。

`.env` 中可以调整 `LOKI_RETENTION`、三个宿主端口和两个观测网段。默认网段为 `10.254.240.0/28` 与 `10.254.240.16/28`，运行前须核对本机路由和已有 Docker IPAM；冲突时调整本套配置，不修改 Docker 全局地址池或删除其他网络。网段检查与镜像检查不能替代宿主机磁盘监测。

本套 volumes 分别保存 Loki 日志、Alloy 读取位置/WAL 和 Grafana 账号/状态。宿主机损坏不由单机 volume 解决；业务数据库审计和备份继续使用各自正式恢复合同。

Docker 首次回读或读取位置丢失时，旧记录可能落在相应 stream 的乱序接收窗口之外，产生 `too_far_behind` 拒绝；七天保留期不表示可以完整回补七天历史。排查须同时核对 Alloy 丢弃计数的增量、诊断时间和 Loki 拒绝原因，区分历史回读失败与当前采集故障，不修改原始时间戳来掩盖丢失。

1. 查看本套状态：`node scripts/observability.mjs --status`。同时输出 Loki、Alloy ready/healthy、Grafana 四项健康结果，失败退出非零。Loki 就绪为 `http://127.0.0.1:3110/ready`，Alloy 组件健康为 `http://127.0.0.1:12346/-/healthy`；HTTP 健康仍需结合容器健康状态、采集指标和实际日志查询判断。
2. 停止：`node scripts/observability.mjs --stop`。该命令保留 volumes、凭据与源日志。
3. 恢复：使用同一 checkout、相同固定镜像和相同 `.env` 执行 `--start`，读回历史查询与新的日志，并核对读取位置、WAL 和告警评估。
4. 升级或回滚：先保留当前镜像 digest、配置与三个 volume 的备份，验证 Grafana/Loki 数据格式兼容。删除 volume 不属于停用或回滚动作。

实际磁盘增长量、保留期清理、断网恢复范围与通知送达都需目标运行证据；配置存在不等于这些验证已完成。
