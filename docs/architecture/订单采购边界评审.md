# 订单 / 采购边界评审 / Order / Purchase Boundary Review

## 结论

`sales_order` 是客户承诺及本单价格条件的业务源单据，不是出货事实。`purchase_order` 是采购承诺及本单付款 / 开票条件，不是采购入库事实。当前已经存在的 `purchase_receipts / purchase_returns / purchase_receipt_adjustments + inventory_txns` 承担采购入库、退货、调整和库存落账事实，不重复设计语义相同的事实表。

```text
sales_order = 业务承诺。
sales_order_item = 承诺明细。
purchase_order = 采购承诺。
purchase_receipt = 采购入库事实。
shipment = 出货事实。
inventory_txns = 库存落账事实。
AR/AP = 财务事实。
```

## 销售订单 / Sales Order

`sales_orders` 应记录客户订单承诺：

- customer_id / customer snapshot。
- order_no / customer_order_no。
- order_date。
- expected_delivery_date / ship_date。
- lifecycle status。
- owner / salesperson。
- currency，以及整单唯一的计税方式、税率、报价是否含运费和可空报价运费。报价运费沿用订单币种，不单独保存币种。
- 服务端由明细、运费条件和报价运费派生并持久化的货款金额、税额和订单总额；草稿不完整时允许为空，提交和生效前必须完整。报价不含运费时必须明确填写非负报价运费，报价含运费时另计金额必须为空。
- 从客户默认值带出、允许本单修改并冻结的国家 / 地区、收货人、收货电话和收货地址快照。
- source snapshot / note。

`sales_order_items` 应记录承诺明细：

- product_id 可空；尚无产品时必须填写 requested_product_name，接单后由工程关联产品。
- product_sku_id 可选。
- customer_product_no / product code snapshot、NEW / REPEAT、process_requirement。
- pre_shipment_sample_quantity；生产数量为订单数量加船头样，销售货款只按订单数量计价。
- ordered_quantity。
- unit_id。
- required_date。
- unit_price / amount：草稿可暂缺，提交和生效前必须完整；金额由服务端按数量和单价重算。
- line_status。
- cancelled_quantity / closed reason 可选。

接单页以“订货明细”记录客户要订的产品、数量、单位和交期。新建订单不预置空白明细，可先保存无明细草稿；通过“添加订货明细”录入需求，已添加的明细仍须通过名称、单位和数量校验。提交或生效前继续核对有效明细、价格及整单商务条件。

“从已有规格添加”是复用已有产品规格的可选入口；产品档案、物料清单和打样资料仍由工程完善。“调整明细顺序”只在编辑页至少有两条明细时显示，应用后随订单保存，不表示生产或工序先后。一张订单可包含多款产品，每款的数量和交期分别保留。

`shipped_quantity` 不应作为手工事实字段。它可以是从 shipment facts 重算的派生值或缓存：

```text
shipped_quantity = sum(valid shipment_items.quantity by sales_order_item_id)
```

如果未来缓存 `shipped_quantity`，必须能从 `shipments / shipment_items / inventory_txns` 重算，且不能在没有 shipment facts 时伪造已发货。

## Purchase Order 当前实现

2026-06-15 已新增 `purchase_orders / purchase_order_items` 最小运行闭环，定位仍是采购承诺源单据：

- 后端已落 Ent schema、Atlas migration、repo/usecase、状态机、JSON-RPC 和测试。
- 前端 `/erp/purchase/accessories` 已从 formal shell 切换为采购订单 V1 页面，支持列表、筛选、详情、订单头与明细保存，以及提交、审批、关闭、取消。
- `purchase_receipt_items.purchase_order_item_id` 可选关联采购订单行，用于追溯本次入库来自哪一条采购承诺。
- 采购订单不写 `inventory_txns`、不改 `inventory_balances`、不创建批次、不生成应付 / 发票 / 付款事实。

当前已提供非持久化的采购入库进度读投影：

- `get_purchase_order_receipt_progress` 以采购订单行为 grain，在同一服务端读快照中组合采购承诺、已过账入库 / 数量调整和现有入库草稿。
- 前端“生成采购入库草稿”只消费服务端返回的规范六位小数字符串、可生成结论和原因，不在浏览器重算事实余额。
- 该投影不新增余额表，不改变采购订单、采购入库和库存事实的写入真源。

采购订单头同时保存本单的付款方式、付款周期、是否需要发票、发票类别、预计到货日期、供应商确认到货日期和收货地址：

- 新建时可从供应商档案带出付款与开票默认值；保存后形成本单快照，供应商以后修改默认值不会反向改写历史采购单。
- 不需要发票时必须清空发票类别；需要发票时必须选择类别。
- 供应商确认到货日期和预计到货日期都不能早于下单日期。
- 这些字段描述采购承诺，不代表已收货、已开票、已生成应付或已付款。

仍未实现的范围：

- 工程用料审批可从已确认样品和启用 BOM 生成应需数量；库存可用量和在途量不自动扣减。
- 不提供采购需求、已采购、在途和剩余采购量的综合 read model，也不包含供应商报价、合同审批或应付自动生成。
- 采购入库仍可无 PO 创建，用于历史 / 快速入库或暂未启用采购订单的场景。

采购入库过账已按采购行锁定并计算有效已收量，防止累计超收；读投影复用同一领域口径：

```text
有效已收量 = POSTED 入库 + POSTED 数量增加 - POSTED 数量减少
草稿占用量 = DRAFT 入库行数量合计
剩余可收量 = 采购承诺量 - 有效已收量
剩余可生成量 = max(剩余可收量 - 草稿占用量, 0)
```

合法的草稿占用超过剩余可收量时，读投影仍返回当前数据并以不可生成原因失败关闭；只有已过账事实造成有效已收量小于零或超过采购承诺量时，才把数据不变量破坏作为内部错误拒绝返回。采购退货是独立出库事实，当前不会重开采购承诺或剩余可收量。采购需求、在途或自动应付仍必须基于正式合同另行派生，不能把采购承诺、入库事实和计划需求混成一张表。

## Purchase Receipt 关系

当前 `purchase_receipts / purchase_receipt_items` 已经是采购入库事实源单据：

- posted 后写 `inventory_txns.IN`。
- cancel posted receipt 通过 `REVERSAL` 回退库存。
- 行级关联 material / warehouse / unit / lot。
- 独立 `purchase` JSON-RPC 域负责创建草稿、加行、过账、取消、读取和列表；公开入库 API 只接受采购订单、采购行等已登记的正式来源字段。
- 有采购来源时，过账前锁定采购行并校验采购单已批准、采购行开放；有效已收量为 `POSTED 入库 + 已过账数量增加 - 已过账数量减少`，取消的入库 / 调整不计入。
- 采购退货仍是独立出库事实，当前不自动重开可收数量；如需补收必须先明确产品策略。

`purchase_orders` 与现有 receipt 的关系是：

```text
purchase_order / item = 采购承诺。
purchase_receipt / item = 真实到货入库事实。
```

一个采购订单可以多次入库；一个采购入库可选关联采购订单行，也可能来自无 PO 的历史 / 快速入库场景。当前按采购订单行查询非持久化的入库进度，但不把它保存成第二套余额真源，也不因审批采购订单自动生成采购入库。

## BOM 到采购需求

工程用料复用销售订单入口，新增 `engineering_material_requests / items` 作为审批源单，不建立第二套 BOM 或库存真源。

1. 接单时记录需求、参考附件、数量、交期和预付款条件；工程可在订单草稿阶段建立产品、图样和 BOM 并打样。预付款条件不代表实际到账，到账以财务收款记录为准。
2. 工程在订单行保存 `PREPARING → SAMPLING → CONFIRMED`。确认须有样品说明，绑定 BOM 内容指纹与产品图片；改样须先有原因退回。返单可显式沿用同客户、同产品规格、相同资料的已确认样品，保留来源订单行。
3. 订单生效、样品确认且 BOM 启用后，工程提交用料汇总。生产数量 = 订单数量 + 船头样；每部位用量 = 生产数量 × 单位用量 × (1 + 损耗率)，逐部位保留六位小数后按材料和单位汇总。片数不重复相乘。
4. 老板审核后，另一位财务人员可展开材料的产品、BOM、部位和工艺来源，核定实际采购数量、人民币单价和到货日；调整数量须注明原因。原料库存、在途、包装采购仍由岗位核对，不做未定义的自动净需求抵扣。
5. 财务批准在同一事务中按厂商生成 `approved` 采购单；零采购量不生成采购行。采购单保留审批来源，重复请求不得生成第二批单据。退回保留原因和审核历史，工程重新提交产生新审批记录。
6. 用料提交后对应工程来源锁定；审批核对当前来源，来源变动必须退回后重新提交。关联销售订单的生产发布同时校验样品、量产 BOM 和用料批准；接单生效本身不放行量产。

采购、收货、质检、入库和收付款仍保持原有事实边界。当前用料审批是领域源单和销售列表待办状态，不宣称已自动加入 Workflow 任务收件箱。

## 采购下单与真实入库分离

| 概念 | 表 | 影响库存 | 说明 |
| --- | --- | --- | --- |
| 用料审批 | `engineering_material_requests / items` | 否 | 按订单和已确认 BOM 汇总，经两级审批形成采购承诺 |
| 采购承诺 | `purchase_orders / purchase_order_items` 已有 | 否 | 已向供应商下单 |
| 采购入库事实 | `purchase_receipts / purchase_receipt_items` 已有 | 是 | 到货验收入库，posted 后写库存 |
| 采购退货事实 | `purchase_returns / purchase_return_items` 已有 | 是 | 退供应商，posted 后扣库存 |
| 采购入库调整 | `purchase_receipt_adjustments / items` 已有 | 是 | 入库后数量或 lot/warehouse 更正 |

`purchase_order` 不能替代 `purchase_receipt`。Workflow 的采购跟进也不能替代采购事实。

## 出货放行与真实出货分离

当前正式入口由 `finished_goods_delivery` 创建 Shipment 财务 approval；审批通过后，绑定领域命令只把 Shipment 版本化财务放行门禁写为 `APPROVED`。历史 `shipment_release done -> shipping_released` 只保留既有协同读取语义，两者都不等于真实出货。

禁止：

- 从财务 approval、`APPROVED` 门禁或历史 `shipping_released` 写 `inventory_txns.OUT`。
- 从财务 approval、门禁或历史投影生成 AR/AP、invoice、payment。
- UI 把财务已放行或 `shipping_released` 显示为已出库 / 已发货 / 已扣库存。

`shipped` 只能由当前 `OperationalFactUsecase` 的 `ship_shipment` 事务支撑；该事务重新校验财务门禁、质检、销售来源、预留和可用库存，再同时写 Shipment fact 与 outbound inventory transaction。sales order 未出货数量应从 shipment facts 重算：

```text
unshipped_quantity = ordered_quantity - valid_shipped_quantity
```

出货单可冻结销售订单的收货快照，并记录运输方式、承运商、物流 / 提单号、件数 / 箱数、毛重、体积、唛头、行包装说明、箱号以及本次实际运费。实际运费金额可空；填写时币种必须沿用销售订单币种并由服务端复核，使同一出货单及其来源业务链保持一个币种。该字段与销售订单报价运费保持独立，不回写报价运费或销售订单总额，不等于物流应付，也不自动创建发票或付款事实。

## 财务边界

财务应付不应从 purchase order 或 shipment 的实际运费字段直接生成，至少要评审采购入库、物流对账、发票和付款口径。

建议口径：

- AP candidate 可以基于 posted purchase receipt / accepted invoice / reconciliation 评审。
- AR candidate 至少应在真实 shipped 后评审。
- invoice / payment / reconciliation 是财务事实，不由 Workflow done 或 source document status 直接伪造。

