# 各类流程建模边界评审 / Flow Modeling Boundary Review

## 结论

plush-toy-erp 的流程建模直接由当前 Product Core、Workflow / Fact、RBAC、页面和客户配置边界定义。

当前要做的是“按项目实际做流程建模”，不是照搬通用 ERP 流程平台。“流”描述允许怎样运转；一次真实运行按对象和顺序形成的“链”另见 [业务链与运行轨迹边界](业务链与运行轨迹边界.md)。

```text
业务流 = Product Core 主链路和来源关系
状态流 = 业务对象生命周期、协同状态和事实状态
工作流 = ProcessRuntime 具体实例 / 节点 + WorkflowTask 协同责任
审批流 = 工作流中处理审核、同意、拒绝、退回等决定的部分
任务流 = 单条任务的创建、办理、阻塞、恢复、转交、完成、退回和催办
异常流 = 驳回、退回、阻塞、恢复、取消、冲正、返工和补偿等不同动作
通知流 = 任务提醒、催办、超期和看板风险提示
自动流转 = 已评审的 ProcessRuntime 路由、绑定领域命令或领域 usecase 规则
规则 / 策略 / 扩展点 = 先进入配置、客户差异和专题评审，不直接变 runtime 平台
```

本文件是架构评审，不代表新增 schema、migration、API、RBAC、菜单、页面、ProcessRuntime、WorkflowUsecase 或 Fact usecase。当前 runtime 仍以代码、Ent schema、Atlas migration、测试和 [当前真源与交接顺序](../当前真源与交接顺序.md) 为准。

## Plush 建模总图

这张图回答：各类“流”在本项目里如何归属，哪些可以进入页面表达，哪些必须回到后端或正式评审。

```mermaid
flowchart TD
  scope["项目业务边界<br/>Product Core / 当前客户范围"]
  productCore["Product Core 主链路<br/>MasterData / Source Document / Fact"]
  stateBoundary["状态流<br/>业务生命周期 / 协同状态 / 事实状态 / 派生结果"]
  workflow["Workflow 协同层<br/>ProcessRuntime 实例 / 节点<br/>WorkflowTask / events"]
  facts["Fact usecases<br/>采购 / 库存 / 质检 / 生产 / 委外 / 出货 / 财务"]
  page["页面表达<br/>状态、任务、动作入口、异常原因、可读反馈"]
  customer["Customer Config / Delta<br/>客户差异、菜单、字段显示、导入草案"]
  review["专题评审<br/>规则、策略、自动流转、扩展点"]
  forbidden["当前不做<br/>tenant_id / 流程模板平台 / BPMN / 扩展点注册"]

  scope --> productCore
  scope --> stateBoundary
  productCore --> workflow
  productCore --> facts
  stateBoundary --> workflow
  stateBoundary --> facts
  workflow --> page
  facts --> page
  customer --> page
  customer --> review
  review --> productCore
  review -. 不直接进入 .-> forbidden
  scope -. 未评审不进入 .-> forbidden
  page -. 不决定流程和事实 .-> workflow
  page -. 不伪造事实 .-> facts
```

页面只能展示和触发已存在或已评审的能力。页面不能决定流程路径，不能把任务完成写成事实完成，也不能用客户差异或 mock 数据补造后端事实。

## 各类流的项目落点

| 流类型 | 在 plush 的正式归属 | 当前已有落点 | 页面可以表达 | 当前不做 |
| --- | --- | --- | --- | --- |
| 业务流 / Business Flow | Product Core 主链路、来源关系和模块边界 | `customers / suppliers / contacts / sales_orders / purchase_orders / purchase_receipts / quality_inspections / inventory / shipments / operational_fact` 等能力按台账进入不同成熟层级 | 当前模块处于主链路哪里、来源单据、剩余量、下一步动作 | 不做一张万能流程表，不恢复 `business_records` |
| 状态流 / State Flow | 业务对象生命周期、Workflow 协同状态、Fact 对象状态、派生结果状态 | `状态工作流事实边界.md` 的五层状态和状态词典树 | 状态标签、禁用原因、终态只读、可执行动作 | 不把每个审批节点都做成业务状态 |
| 工作流 / Workflow | 具体 ProcessRuntime 的实例 / 节点运行，以及 WorkflowTask 的协同责任、事件和投影 | 七条正式 ProcessRuntime；`process_instances / process_node_instances / workflow_tasks / workflow_task_events / workflow_business_states` | 业务轨迹、待办、任务详情、处理动作和失败原因 | 不新增第二套通用模板 / BPMN / 低代码引擎，不把具体运行时误写成不存在 |
| 审批流 / Approval Flow | Workflow 的决定子集；由 approval 节点、责任池、能力与领域审批命令表达 | 销售、采购、Shipment 财务放行三项可配置责任；退货、收付款、库存调整、生产异常四项固定责任合同 | 同意 / 退回、原因、审批责任和决定结果 | 不把审批决定等同 Source 已执行、Fact 已过账或完整业务流 |
| 任务流 / Task Flow | 单条 WorkflowTask 的创建、办理、阻塞、恢复、转交、完成、退回和催办 | `/m/<role>/tasks`、桌面任务抽屉、owner / assignee / pool、`workflow_task_events` | 我的任务、角色任务池、本任务处理记录和当前可执行动作 | 不把一条任务事件拼成跨节点完整审批链，不让任务端直接过账 Fact |
| 异常流 / Exception Flow | 各对象状态机、ProcessRuntime / Workflow 异常与领域取消 / 冲正 / 返工 / 补偿 | `blocked / rejected / resume`、领域取消 / 冲正、生产返工与 durable result compensation | 原因、影响、恢复或替代动作、需人工核对证据 | 驳回、退回、阻塞、恢复、取消、冲正、返工和补偿不是同一动作，不能共用万能状态 |
| 通知流 / Notification Flow | 任务 payload、催办、超期、看板风险和后续通知专项 | [通知预警催办与升级第一版](../workflow/通知预警催办与升级第一版.md)、任务看板和 Dashboard 聚合 | 催办状态、超期、风险、最近动作 | 当前不新增独立 notifications 表或消息平台 |
| 自动流转 / Auto Flow | 已评审的 ProcessRuntime 路由、绑定白名单领域命令或领域 usecase 规则 | 七条正式图的节点推进、分支和 durable result；领域事务产生的必要来源协同 | 可展示“系统已生成 / 已关联”的权威读回 | 不从页面本地生成事实，不从 approval / Workflow done 补造库存、出货、生产、核销或财务 |
| 规则 / 策略 | 模块实施治理、客户差异策略、RBAC、后端 usecase 专题评审 | 角色权限、任务 owner / assignee、来源生成规则、字段来源规则 | 可读的禁用原因、不可生成原因、角色可见性 | 当前不做通用规则引擎或业务人员可编辑流程规则 |
| 扩展点 / Extension | Customer Config / Customer Extension 评审后再定 | yoyoosun 客户配置草案、客户交付矩阵中的差异决策、多客户私有化复制包 | 客户菜单、字段显示、品牌等低风险投影 | 不新增 `tenant_id`、runtime plugin、客户代码 hook、扩展点注册 |

## 页面设计口径

页面设计只吸收这些建模结果，不直接实现流程平台。

| 页面元素 | 应该回答的问题 | 必须校验 |
| --- | --- | --- |
| 状态标签 | 这个对象当前处于哪个层级的状态 | 标签是否把协同状态误写成事实状态 |
| 主操作按钮 | 用户点击后真实发生什么 | 是否有后端 API / RBAC / usecase 支撑 |
| 任务抽屉 / 任务详情 | 谁负责处理、当前能做什么、为什么不能做 | owner_role_key、assignee_id、终态、原因必填 |
| 业务轨迹 | 来源 ProcessRuntime 已经执行、当前或受阻到哪里 | 持久化实例 / 节点、attempt、任务锚点；不排列未选未来分支 |
| 本任务处理记录 | 当前任务自身发生过什么 | 任务事件、版本、操作者、角色和原因；不称完整审批链 |
| 来源选择 / 生成入口 | 从哪个 Source Document 或 Fact 行生成 | 来源 ID 是否隐藏、用户只看业务单号 / 行号 / 余额 |
| 异常和禁用提示 | 为什么不能继续、替代动作是什么 | 是否暴露可执行下一步，而不是只给技术错误 |
| 看板和统计 | 反映事实、协同还是派生结果 | 是否可从后端返回或正式 read model 解释 |

页面不得出现以下暗示：

- `shipment_release done` 等于已出库、已扣库存、已生成应收。
- 任务完成等于采购、质检、库存、出货、财务事实已落账。
- 客户配置包等于 SaaS tenant。
- 未经本项目正式评审的流程模板、扩展点或 tenant 字段已经进入当前 runtime。

## 当前实施顺序

本项目按可验证闭环推进流程建模，不一次性建设通用流程平台。

1. 先确认业务对象和事实真源：MasterData、Source Document、Fact 和 Derived 各自归属。
2. 再确认状态流：生命周期状态、协同状态、事实状态和派生结果不要混用。
3. 再落具体 ProcessRuntime 与 Workflow 规则：节点、责任、路由、版本、幂等、权限、异常和领域命令必须由后端合同承接。
4. 再接页面：页面只展示可解释的状态、任务、动作、来源和异常，不补造事实。
5. 最后评审客户差异、规则策略、通知和自动流转：只有多客户或真实使用反馈证明需要时，才进入 Customer Config、Industry Template 或后端 usecase。

## 明确暂不进入实现

以下能力不进入当前 plush runtime：

- `tenant_id`、SaaS 多租户、license server、套餐计费。
- 第二套通用流程模板平台、任意动态节点 / 状态机、BPMN 或拖拽流程设计器；当前具体 `process_instances / process_node_instances` 继续作为七条正式图的运行真源。
- 规则引擎、流程模板导入、策略绑定导入、扩展点注册。
- 允许客户代码直接改核心状态、库存、出货或财务事实。
- 为每个客户复制一套业务代码或用 `if customer == xxx` 分散客户差异。

如果后续确实需要上述任一能力，必须先按 [模块实施治理](../product/模块实施治理.md) 做 docs-only review，写清真源、禁止项、schema 是否必要、RBAC、测试和退出条件，再拆下一轮实现任务。
