# 部署真源约定 / Deployment Conventions

## 当前口径

- 当前唯一部署真源：`/Users/simon/projects/plush-toy-erp/server/deploy/compose/prod`
- 当前仓库只保留 `docker compose` 这一路径，未初始化 `lab-ha`、Kubernetes 和 dashboard
- 目标服务器配置较低，部署时不在服务器构建；服务端和前端镜像必须先在本地或 CI 构建完成，再上传到服务器加载运行
- 线上 migration 使用宿主机 `/usr/local/bin/atlas`，不要拉起 `arigaio/atlas:*` 临时容器，也不要把 Atlas 写入业务 Compose
- 如果后续确实需要第二套部署方式，先补文档和目录，再补脚本和发布流程

## 目录职责

### `server/deploy/compose/prod`

- 单机或单宿主机部署入口
- 保留 PostgreSQL、Jaeger、业务容器和线上迁移脚本
- 所有运行时参数优先通过 `.env` 覆盖，不要直接硬改 `compose.yml`
- 第三方基础镜像必须固定版本 tag；PostgreSQL、Jaeger 和业务镜像都不能使用 `latest`，生产 `.env` 由 `production-preflight.sh` 阻断浮动 tag、placeholder secret、debug 写入开关、PostgreSQL 非 loopback 暴露、后端 HTTP 非 loopback 暴露和 Jaeger 非 loopback 暴露。yoyoosun 的短信能力以 `deployments/yoyoosun/env/runtime.contract.json` 为部署级真源，env、容器与 `auth.capabilities` 任一不是 `provider / enabled / not-mock` 都不得发布
- 服务器侧只允许执行 `docker load`、`docker compose up`、宿主机 Atlas migration 与 smoke；不要执行 `docker build`、`pnpm build`、`go build` 或其他重构建命令
- 服务端镜像内置 Chromium / CJK 字体用于在线 PDF，PDF 浏览器路径、并发和容器内存预算统一从 `.env` / Compose 管理

## 不可变制品与本地演练

发布候选必须从 clean current HEAD 的 committed archive 构建。`scripts/deploy/release-artifact-bundle.mjs --execute` 固定生成 `linux/amd64` Server / Web 镜像，并把 40 位 Git SHA、image content ID、loadable tar checksum、CycloneDX 依赖 SBOM、Atlas migration 序列和客户配置源指纹写入同一脱敏 manifest。manifest 中的客户配置只证明 Product Core 已提交来源，不替代目标 active revision / effective session 读回。

`scripts/deploy/local-release-rehearsal.mjs --execute --manifest <path>` 只使用唯一 `server/deploy/compose/prod/compose.yml`。每次创建 `plush_erp_release_<run-id>`，按 `status → validate / dry-run → apply → status / readback` 执行 migration，并验证 health、ready、release identity、管理员登录、本地测试配置的正式控制面协议、PDF、备份恢复和移除 bootstrap secret 后的重启恢复。无论成功失败都执行精确 Compose 清理；长期 `plush_erp`、共享库和 133 不在该演练的写入范围。

正确顺序是：当前改动的最小充分本地验证与 clean commit → 非强制 push → R640 同 SHA 普通 CI 七分片、聚合和 `CI Gate` 绿色 → release 复用该 CI terminal，仅构建一次候选制品 → 用同一 bytes 完成隔离发布演练并冻结回执 → 登记含演练 digest 的不可变 Release → 只对正式登记目标执行 preflight / rollback point / backup / migration / Compose / smoke。目标机只 load / pull 已构建制品，不从源码重建；任何 SHA、content ID、migration、active config 或 rollback 身份不一致都停止。九岗位生命周期验收和客户 UAT 仍是独立证据，不由 CI 或基础 smoke 代替。

## GitLab CI/CD、GitHub 镜像与固定目标 promotion

- `.gitlab-ci.yml` 是 canonical 验证与发布入口：merge request 运行 affected；main push 由唯一 prepare cache writer 之后并行 static、Node、Web、Server/PostgreSQL、resource-sensitive、browser 和 security 七个固定分片，aggregate 签发可复用 exact-SHA strict terminal，稳定汇总 job 为 `CI Gate`。受保护 release pipeline 只回读该普通 push CI 证据，不重跑 strict；同 SHA 只构建一次不可变候选制品，复用同一候选包演练并登记 GitLab Package/Release。
- `.github/workflows/ci.yml` 只响应 PR、经过 review receipt 与单独 push 授权的 `review/gpt/**`、手工审查，不响应镜像 main。GitHub main 只接受 GitLab protected-main mirror，审查 ref 不从 GitHub 合并 main；GitHub 不能与 GitLab 主 release 同时运行，也不能把 `github-actions` 回执冒充 `gitlab-ci` 主链回执。当前 `.github/workflows/release.yml` 在 checkout、registry 登录、构建或上传前固定失败关闭；只有未来同一 canonical 演练回执与 v2 七资产合同完整接入后，才可另行恢复应急发布。
- 新 GitLab publication 固定使用 `plush.release-manifest/v2`，并把 checksums、artifact manifest、release manifest、SBOM、两个 loadable image tar 和同一 `release-rehearsal.json` 共七项固化到 Generic Package 与 Release。registry、Package、Release、演练回执和目标 promotion 必须绑定同一 40 位 SHA、artifact digest 与 rehearsal digest。旧 `plush.release-manifest/v1` 六资产只允许精确读取、目录展示、校验和既有回滚点兼容；不得补传、重新封装或作为新 promotion 输入，`promotionEligible` 必须为 false。
- promotion、smoke 和 rollback 复用已发布制品，不回到 strict 或 build。新 promotion 只接受 v2 七资产，校验并传递 manifest 绑定的同一 `release-rehearsal.json`；目标机只验证、归档和 load。Release 已存在且身份完整时幂等复用；同版本异 SHA、digest 或 rehearsal receipt 必须阻断。
- `scripts/deploy/deployment-targets.json` 只登记当前可执行的 `demo-133` 与 `customer-test-133`。目标机、用户、根目录、Compose project、env、数据库、上传、端口和公网入口都来自固定 registry，不接受浏览器或命令行临时覆盖。
- `demo-133` 是项目方造数/演练环境，内部 `customer-trial-133` 数据合同只能在该目标重放模拟数据；`customer-test-133` 是甲方测试/验收环境，普通 promotion 默认保留现有业务数据，只有开始新一轮测试且明确选择干净基线时才独立重建，不能继承 demo 造数。
- `erp` 是未来生产环境，只有正式启用并补齐独立 target、备份、回滚、smoke 和生产门禁后才可加入。根域 `yoyoosun.net` 暂时使用 `302` 跳转到 `https://erp.yoyoosun.net`，该导航行为不等于启用生产 target。`admin.yoyoosun.net` 退役后仍绝不进入 CI/CD 环境矩阵、target registry、环境变量映射、数据清理、健康检查、发布验证或回滚流程。
- DEV-only `/__dev/version-center` 通过 loopback Bridge 默认调用固定 GitLab adapter 和固定目标执行器；只有服务端显式 `PLUSH_DELIVERY_PROVIDER=github` 才切到应急 adapter。所有写操作先形成 operation，再要求完整确认串；同一目标只能有一个执行器，终态和 `not_proven` 不自动重试。
- 任一目标需要 fresh 数据代时，独立走 `database-rebuild-controller.mjs` 的只读资格计划和 `database-rebuild-executor.mjs` 的精确确认。它绑定目标当前运行的 exact release，不要求先发布新版本；如果同次既要部署新版本又要建立干净基线，先完成默认保留数据的 promotion 并读回 exact release，再对该 release 独立重建。该路径保持目标登记的逻辑库名不变，fresh backup 恢复校验后保存旧物理数据目录并创建新数据代；不直接清表、不删除旧数据代、不自动 down migration。demo 可在重建后重放模拟数据；test 只建立最小可登录的干净业务基线。
- 普通代码回滚只允许 migration 序列与客户配置源指纹完全相同的旧 manifest；不自动 down migration，也不自动恢复数据库。schema 不兼容时改走 forward-fix 或单独评审、验证过的备份恢复。

### demo、test 与未来 erp

当前两个非生产环境必须相互独立：`demo.yoyoosun.net` 供项目方造数、演练、培训和回归；`test.yoyoosun.net` 供甲方测试/验收，普通部署持续保留甲方已经录入的数据，开始新一轮测试时可通过独立重建 operation 恢复干净基线。二者部署同一不可变 release digest，但数据库、上传目录、Compose project、端口、runtime env、备份、rollback point、operation 与 smoke 全部独立。

未来 `erp.yoyoosun.net` 才可能成为生产环境；在正式登记生产 target、数据保留、备份恢复、权限、smoke 和回滚合同前不得从 CI/CD 执行。根域临时跳转和生产 target 身份必须分开证明。任何数据库清理仍走精确重建 operation，不执行裸清表、volume 删除、临时 SQL 或跨环境复制。当前登记两个 target 不表示立即清理 test，普通 promotion 不含清理意图。

当前远端 promotion / rollback 脚本能证明制品、备份恢复检查、migration、Compose、health、ready、Web health 和运行 SHA；数据库重建 passed 回执另外只证明 fresh 物理代、一次性管理员和空业务基线。客户配置、九岗位数据、51 项浏览器/PDF、带凭据岗位矩阵与客户 UAT 仍是独立未证明项，必须在真实发布后补齐，不能由基础 smoke 替代。

## 单一真源规则

1. 同一环境只保留一条主路径，不额外再并存另一套同级部署脚本
2. 发布、迁移、烟测、文档都围绕 `server/deploy/compose/prod` 收口
3. 若引入新的部署方式，必须同步更新：
   - `README.md`
   - `docs/当前真源与交接顺序.md`
   - `server/deploy/README.md`
   - 对应脚本和验证命令

## 变更流程

涉及部署改动时，按这个顺序做：

1. 先确认改动是否属于 `server/deploy/compose/prod`
2. 优先修改 `.env.example`、`compose.yml`、发布脚本和对应 README
3. 再执行最小校验
4. 最后同步更新文档
