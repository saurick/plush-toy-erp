# 角色权限矩阵 / Role Permission Matrix

## 当前口径

**功能权限回答“能做哪类动作”，业务归属和状态回答“能否处理这一条记录”。** 菜单、角色名和前端隐藏都不是安全边界。

| 要核对的问题 | 阅读位置 |
| --- | --- |
| 权限从哪里来，谁能进入手机端 | 本节 |
| 数据范围、敏感字段和附件 | [权限分层](#权限分层与当前完成度) |
| 使用哪个权限码、默认给哪个岗位 | [关键权限码](#关键权限码)、[预设角色](#预设角色) |
| 停用、注销、角色变更与审计 | [操作边界](#操作边界) |

### 权限与菜单真源

`admin_users → admin_user_roles → roles → role_permissions → permissions` 是当前 RBAC 路径；权限码和内置角色由 `server/internal/biz/rbac.go` 定义。登录及 `auth.me` 返回管理员、角色、权限和后端菜单，两端只消费投影。

旧 `admin_users.level / menu_permissions / mobile_role_permissions` 不再授权。禁用角色不授予权限；`permissions` 没有独立 disabled 字段，停用须移除角色绑定，或从 `rbac.go` 移除后由后端归一清理。

| 菜单条件 | 判断规则 |
| --- | --- |
| `RequiredAny` | 至少具备其中一项 |
| `RequiredAll` | 必须全部具备 |
| 同时存在 | 两组均满足 |

当前共享页和产品 / SKU 聚合页按相关读取能力的任一项开放，页内 API 与动作继续独立鉴权。目前没有必须组合权限的正式菜单，`RequiredAll` 合同与测试保留供正式扩展。

### 手机入口与超级管理员

| 身份 | 入口与办理边界 |
| --- | --- |
| 普通账号 | 入口只认 `mobile.<role>.access`；`auth.me.roles` 用于身份、归属和审计，不能替代入口权限 |
| super admin | 全环境可从 `/m/all/tasks` 查看，也可选岗位，不需绑定全部业务岗位；可选岗位仍取 active revision 有效岗位与入口动作交集 |
| 普通 `admin` | 不等于 super admin，无全局查看特权，仍须通过角色获权，也不能任意修改 super admin |

super admin 的全权限用于初始化与紧急管理；“全部 / 单岗位”只改变查看范围，不改实际角色、任务或审批责任及审计身份。处理任务仍检查 owner / assignee、状态与领域命令。未配置、停用或撤权岗位不能进入。

### 任务办理、监督与转交

| 动作 | 权限与限制 |
| --- | --- |
| 老板审批完成 | `workflow.task.approve`，再验任务归属和状态 |
| 其他完成 | `workflow.task.complete`，再验任务归属和状态 |
| 退回 | `workflow.task.reject` |
| 阻塞、催办 | `workflow.task.update`；催办必须留事件 |
| 跨岗监督 | `workflow.task.supervise` 只扩大老板 / PMC 的列表和看板读取，不授予办理或领域事实权 |
| 转交 | 独立 `workflow.task.assign`；当前默认 boss，super admin 全权限可执行，PMC、普通 admin 和其他岗位默认没有 |

转交仅接受 `ready / blocked`，转给同一 `owner_role_key` 下启用且有读取、更新和完成 / 审批能力的人员，或退回原岗位池。能转交不代表有接收资格，super admin 和操作人也不例外。

成功转交只改个人归属，留下事件、幂等 receipt 和运行审计，不改任务状态或业务事实。完整动作与重放规则见[Workflow 合同](../architecture/状态工作流事实边界.md#公共-api-边界)。没有独立跟单岗位时由 sales 或 pmc 承接，不另造角色。


## 权限分层与当前完成度

### 手册维护权限

帮助中心的三册企业补充分别使用 `help.business.edit / publish`、`help.administration.edit / publish`、`help.operations.edit / publish`。编辑与发布独立授予，普通岗位默认不获得；超级管理员可维护全部已获准章节。章节阅读仍遵循正式手册与岗位 / 页面范围，维护权限不扩大读取范围。

全员可反馈自己有权阅读的章节，普通读者仅能看本人纠错；对应手册维护者可处理可读章节的纠错。具体使用见[手册维护](../manuals/README.md#在线纠错与企业补充--help-contributions)。

### 六层权限各管什么

权限中心不建立独立页面授权，也不把所有业务字段做成角色勾选项。页面入口从客户模块状态和角色功能权限推导；字段权限只用于后端能够统一保护的敏感字段组。

| 层级 | 解决的问题 | 当前状态 |
| --- | --- | --- |
| 客户能力配置 | 当前客户是否启用某个业务模块 | 已由 customer config revision 发布、激活和回滚控制 |
| 功能权限 | 当前角色能查看、创建、修改或审批什么 | 已由 RBAC 权限码控制 |
| 数据范围 | 当前角色能操作哪些客户、订单、仓库或财务数据 | Workflow 任务已有责任岗位 / 指定处理人约束；仓库资源已支持角色级 `ALL / ASSIGNED / NONE` 并由后端查询与写入强制执行，其他业务资源仍未形成统一策略 |
| 敏感字段 | 成本、结算账户、联系方式等是否可见、可修改、可导出或可打印 | 已建立 4 个只读敏感字段组，由服务端对响应、嵌套来源快照及打印取数递归脱敏；尚未宣称通用修改 / 导出动作已全部按字段组闭环 |
| 状态与归属 | 当前状态是否允许操作、任务是否属于当前处理人 | 已由领域 usecase、状态和 Workflow 归属共同控制 |
| 页面与按钮 | 给用户展示哪些入口和动作 | 只作上述能力的前端投影，不是授权真源 |

岗位设置维护功能权限、仓库范围与敏感字段组；权限地图只读解释 RBAC、active revision、模块状态和岗位投影的交集，不反向授权。页面分区及保存流程统一见[菜单与岗位设置](../product/菜单与正式入口合同.md#帮助与岗位设置)。

### 仓库范围与来源读取

采购收货按整张单据执行仓库范围：所有明细仓库均在当前账号范围内，才可读取单头和完整明细、追加明细、过账或取消。列表在分页和计数前排除含范围外明细的单据，`NONE` 返回空列表；没有明细且尚无仓库归属的单头只对 `ALL` 可见。新增明细还检查新仓库，过账、取消和幂等读回在后端检查当前完整仓库集合及相关库存事实，不能靠客户端仓库筛选取得部分单据。物料供应流程的收货生成与入库执行使用同一仓库范围；流程已完成后的幂等读回仍检查当前事实归属，范围不进入命令指纹或流程快照。

采购到货与来源退货命令只接收数量、仓库办理信息和来源标识。采购退货从已入库单或不合格质检推导供应商、材料、单位、批次和价格，不要求办理岗位拥有采购商业信息读取权限；仍需退货业务权限、来源读取权限、客户模块能力及仓库范围。客户端传入单价、金额或改写来源粒度的字段必须拒绝，无商业信息读取权限的响应继续隐藏价格和金额。

### 附件与扩展边界

财务附件按所属 `finance_fact` 的持久化 `FactType` 使用应收、应付、发票或对账的读取 / 确认权限。财务报表读取不授予原始附件访问；撤销后的幂等读回继续检查所属类型的读取权限和原撤销人、原因。

后续扩展数据范围仍采用按业务资源定义的小型固定策略；当前只有仓库资源具备稳定归属真源，订单本人负责、部门或客户集合等范围尚未实现，不能把页面默认筛选宣传为数据隔离。敏感字段继续使用稳定领域字段组；当前已保护查询响应、来源快照和打印取数，新增修改、导出或其他 API 时必须显式接入同一后端策略，前端隐藏列不能代替后端保护。

| 模块 | 权限码 | 用途 |
| --- | --- | --- |
| 系统 | `system.user.read/create/update/disable/revoke`、`system.user.role.assign` | 管理员账号读取、创建、更新、临时启停、正式注销和独立角色分配 |
| 系统 | `system.role.read`、`system.permission.read`、`system.role.permission.manage` | 查看角色与权限定义、维护允许编辑的业务角色功能权限 |
| 桌面入口 | `erp.workbench.read`、`erp.business_dashboard.read`、`erp.print_template.read`、`erp.business_chain_debug.read` | 岗位工作台、管理业务看板和其他后台入口分权 |
| 主数据 | `customer.*`、`supplier.*`、`contact.*` | 客户、供应商和联系人 动作权限 |
| 销售订单 | `sales_order.*`、`sales_order_item.*` | 销售订单和订单行 动作权限 |
| 工作流 | `workflow.task.read/supervise/create/update/assign/approve/reject/complete` | 任务查询、跨责任池只读监督、创建、更新、受控转交、审批、驳回和完成；监督权限不授予动作 |
| 采购入库 / 退货 | `purchase.receipt.read/create/post/cancel`、`purchase.return.read/create/post/cancel` | JSON-RPC、usecase/repo 按来源、状态与仓库范围共同校验，过账和取消分别控制 |
| 岗位任务端 | `mobile.<role>.access` | 岗位任务端角色入口，例如 `mobile.sales.access` |
| 调试 | `debug.seed`、`debug.cleanup`、`debug.business.clear`、`debug.business_chain.run` | 开发 / 测试调试能力 |

| `quality` | 品质 | IQC、成品抽检、异常处理、返工复检、品质岗位任务端 | 只能处理 `owner_role_key=quality` 或 `assignee_id=自己` 的任务 |
| `finance` | 财务 | 应收、应付、收付款、对账、财务报表、财务岗位任务端 | 只能处理 `owner_role_key=finance` 或 `assignee_id=自己` 的任务 |

## 操作边界

### 账号停用与注销

- 管理员账号状态由 `disabled` 与 `revoked_at` 派生为 `active / suspended / revoked`。临时禁用可恢复；正式注销保留账号和历史身份，不物理删除，也不能通过普通启用恢复。
- 临时禁用、正式注销和重置密码都在同一事务递增 `auth_version` 并注销该账号全部 active `admin_sessions`。审计只记录注销会话数量和稳定原因，不保存 session key；重复设置相同禁用状态保持幂等，不重复递增版本、注销会话或写审计。

正式注销还会在同一事务将该账号未完成的个人待办退回原岗位任务池；超级管理员和当前操作人不能被该路径注销。
### 系统角色与凭据管理

- `admin` 与 `debug_operator` 是 `role_type=system` 的产品系统角色，权限组合只读；是否可分配仍以服务端针对当前管理员返回的 `assignable_by_current_admin` 为准，不能在前端把 system role 一律判为不可分配。`business_default` / `custom` 同样消费该 metadata。非超级管理员不能改手机号、角色、状态或密码来接管持有系统角色的账号。
- 持有 `system.user.create/update` 与 `system.user.role.assign` 的账号属于高信任凭据管理员（credential administrator）：可以为非系统账号建立或恢复登录凭据并分配业务角色，相关动作必须进入控制面审计。“不天然拥有业务事实权”只描述当前账号自己的 RBAC，不等于绝对无法代管其他账号。

  若后续要求管理员绝对不能代持业务账号凭据，应单独评审邀请 / 自助激活、一次性恢复和手机号变更验证合同，不能用局部 guard 假装完成隔离。
- 角色记录以 `role_type` 区分 `system / business_default / custom`，以正整数 `version` 承担角色权限 CAS。相关 schema 变更必须通过正式 Ent / Atlas migration 进入 fresh 与 upgrade 链，不能只依赖 dirty worktree 的 schema 或 generated code。

### 权限维护与业务动作

- 领域事实单据的取消、冲正、删除限制和审计要求由对应 usecase、权限码与表结构定义，不能从其他领域的权限推导。
- 权限中心只展示 `server/internal/biz/rbac.go` 当前内置权限；旧内置权限码从该真源移除后，后端 seed 会清理旧 `permissions` 行和对应 `role_permissions` 绑定，列表接口也不会继续返回历史残留。
- 当前权限中心维护稳定预设角色的功能组合，不开放没有客户配置上限合同的自定义角色创建，也不提供角色物理删除。`system.role.create/update/delete` 已退出正式权限真源，不能用无实现的权限码暗示可用能力。
- 启动 seed 会把 `admin` / `debug_operator` 两个系统角色的代码定义视为产品真源：仅当权限集合真实变化时原子同步并递增版本。`business_default` / `custom` 的人工选择不会被重启覆盖；后续调整业务角色默认权限必须走显式、可审查的数据迁移。
- `admin` JSON-RPC 对每个方法使用精确参数合同，未知字段和未知权限码会整体拒绝，不能静默忽略后返回“保存成功”。
- 可审批必须同时满足权限码、业务归属和状态条件，不能只靠 `admin` 角色推导。
- 可催办必须写入 `workflow_task_events`，不能只是页面红点或备注。
- 可打印和可导出只表示入口权限；当前打印取数已接入敏感字段脱敏，任何新增导出仍须同时执行数据范围与字段组策略后才能宣称安全闭环。
- 移动端只处理当前角色任务和规则允许的风险任务，不展示低代码配置、状态字典或系统权限页面。
