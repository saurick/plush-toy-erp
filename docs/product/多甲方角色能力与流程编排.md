# 多甲方角色能力与流程编排 / Multi-customer Role and Workflow Design

Status / 状态：Current Design Contract。当前实现层级仍以代码、migration、测试和目标环境证据复核。

本文只回答三个问题：Product Core 角色怎样复用到不同客户岗位、页面和动作权限怎样收窄、哪些跨岗位事项进入 ProcessRuntime。它不复制领域事实、字段字典、数据库表结构、测试清单或客户交付状态。

结论：一套 Product Core 通过多角色、模块状态、页面 / 动作投影和责任池适配不同客户岗位。正常业务由领域 usecase 自动校验和过账；只有跨岗位交接、异常、退回及高风险审批进入 Workflow。客户配置不能 fork 代码、提升后端权限、改 schema、改领域状态机或直接写 Fact。

## 角色、能力和责任池

```text
用户 = 一个或多个后端角色
角色 = 后端权限码集合
客户角色投影 = 页面、动作和责任池的收窄配置
流程节点 = 所需能力 + 责任池，不直接绑定公司岗位名或员工
```

客户配置只能在 Product Core 授权上限内收窄。稳定的基础授权公式是：

```text
实际动作 = 后端 RBAC ∩ enabled 模块 ∩ active revision entitlement - 当前角色 revoke

角色有效动作(r)
= (RBAC(r) ∩ enabled module actions ∩ active revision entitlement(r)) - revoke(r)

用户有效动作
= ⋃ 角色有效动作(r)
```

- 单角色先计算自己的 entitlement 与 revoke，多角色账号再取角色并集；一个角色的 revoke 不删除另一个角色正式拥有的能力。
- `access_entitlements` 是客户配置唯一的动作加法真源；`role_profiles` 只保存角色启停、能力包标记和 revoke，不建立第二套加权规则。
- 上述结果只表示基础授权允许。真正执行时还要通过来源读取权限、owner / assignee / 责任池、数据范围、对象状态、版本 / CAS、幂等及领域门禁。
- 页面投影与动作投影分开。页面可见、按钮可见或 super admin 身份都不能代替服务端校验。
- 客户岗位与标准角色不一致时，优先给同一用户分配多个标准角色；只有职责组合长期稳定、多人复用且审计确需独立命名时，才评审客户角色模板。

`system.* / customer_config.* / debug.*` 控制面继续由后端 RBAC、环境门禁和审计保护，不因客户业务 entitlement 配错而失去修复入口；修复入口也不会放开业务事实写入。

## Product Core 角色模板与客户岗位

| 核心角色      | 主要责任                           | 不承担的事实责任                 | 永绅岗位投影                 |
| ------------- | ---------------------------------- | -------------------------------- | ---------------------------- |
| `sales`       | 客户、联系人、销售订单与交付协同   | 不写库存、质检、出货或应收 Fact  | 业务                         |
| `boss`        | 重大异常、备用 / 升级审批          | 不替代日常主办或直接改业务明细   | 老板                         |
| `engineering` | 产品、SKU、工序、BOM 和工程资料    | 不生成采购、生产或库存 Fact      | 工程                         |
| `pmc`         | 排产、缺料和进度风险协同           | 计划完成不等于生产完工或入库     | PMC                          |
| `purchase`    | 供应商、采购订单和到货准备         | 入库与应付仍由领域事实生成       | 采购；财务人员可兼任         |
| `production`  | 加工合同、生产与委外办理、提交完工报告 | 不确认成品入库，不直接写质检、库存或结算 Fact | 生产 / 委外                  |
| `quality`     | 有来源的检验和质量处置             | 质检结论不直接增减库存           | 品质                         |
| `warehouse`   | 收货、采购与成品入库确认、库存、出库和真实出货 | Workflow 完成不代替领域过账 | 主料仓 / 成品仓 / 其他仓岗位 |
| `finance`     | 业务应收、应付、发票、对账和收付款 | 当前不是完整总账、税控或成本会计 | 财务                         |
| `admin`       | 账号、RBAC、客户配置和系统审计     | 不天然拥有业务岗位办理权         | 系统管理员                   |

永绅“财务根据工程表下采购合同”使用同一账号的 `finance + purchase` 多角色组合。采购权限不并入所有客户的 `finance` 核心角色，采购承诺仍回到采购订单与 BOM / 明确批准的需求来源。

## 审批责任与流程选择

当前客户包可从 Product Core 注册表选择六条已登记 ProcessRuntime：

| 业务事项         | Process key                     | 责任配置                         | Workflow 与 Fact 边界                        |
| ---------------- | ------------------------------- | -------------------------------- | -------------------------------------------- |
| 销售订单审批     | `sales_order_acceptance`        | 可配置主办 / 备用 / 升级         | 审批决定是否激活源单，不写库存或财务 Fact    |
| 采购订单审批     | `material_supply`               | 可配置主办 / 备用 / 升级         | 审批决定是否批准源单，不创建收货、库存或应付 |
| 出货财务放行     | `finished_goods_delivery`       | 可配置主办 / 备用 / 升级         | 只写财务放行门禁，不等于真实出货             |
| 收付款审批与执行 | `finance_payment_approval`      | Product Core 固定审批 / 执行职责 | 审批不等于过账，财务显式执行后才写核销事实   |
| 人工库存调整     | `inventory_adjustment_approval` | Product Core 固定审批 / 执行职责 | 审批不改库存，仓库显式过账后才写流水         |
| 生产异常决定     | `production_exception_approval` | Product Core 固定审批 / 执行职责 | 审批只形成决定或额度，事实效果由生产动作写入 |

客户只能选择已登记流程及批准变体，不能增加、删除或重排节点，不能注入脚本、任意 BPMN、状态机、条件表达式或领域命令。销售、采购和出货财务放行三项可维护启停、主办、备用、升级角色或具名成员；其余三项使用注册流程合同的固定责任。

管理员保存审批责任时必须按 active revision / hash 做 CAS，在一个事务中写 immutable revision、完整投影并切换 active；失败整体回滚。新实例读取新 active revision，已启动实例继续绑定冻结 revision，不被后续配置改写。

## 页面、动作和数据范围

- `rolePageProjections` 收窄岗位可见页面；页面需要的客户、供应商、产品、材料、库存批次或来源单读取权限由页面 catalog 明确登记，不因此开放对应维护页面。
- `access_entitlements` 收窄页面内业务动作；模块 `read_only / disabled` 仍由后端模块门禁拒绝写入。
- 当前一客户一库，数据范围只具备全局 / 当前客户的基础能力范围，不能写成已经实现按仓库、业务员或部门的通用行级权限。
- 将来增加 `warehouse_set`、`owner_only` 等数据范围，必须先有固定 catalog，并在每个领域查询和写入中执行后端约束；页面默认筛选不是安全边界。
- 当前运行时字段策略只控制已登记列表 / CSV 列的 `visible`。表单必填、可编辑、标签和业务校验不由客户配置改写，具体边界看[配置与权限策略](配置与权限策略.md)。

## Workflow、事实与链

- `task done`、`blocked` 或 `rejected` 只表示协同结果；库存、质检、出货、收付款等事实必须由各自领域 usecase 过账。
- ProcessRuntime 节点只能调用登记的白名单领域命令。任务 payload 和流程页面不是 Source Document 或 Fact 真源。
- 审批人、业务执行人和事实写入人可以不同；super admin 不能用管理身份冒充业务岗位。
- 链是持久化历史的不可编辑投影；客户配置只能收窄查询和展示，不能补写、删除、改序或把局部任务记录冒充完整业务链。

状态 key、节点终态、幂等、恢复、补偿和并发合同不在本文复制，统一回到[状态工作流事实边界](../architecture/状态工作流事实边界.md)、代码、schema、migration 和测试。

## 当前边界与验证

- 当前工作树登记的是上述六条 ProcessRuntime；销售、采购和出货财务放行开放审批责任配置，收付款、库存调整和生产异常使用固定责任。是否已经在目标环境启用，必须读回 active revision 和 effective session。
- `businessFlows / stateMachines / processPolicies` 等预览配置不等于运行能力；未登记的 PMC / 工程自由审批不能由文档或客户包伪造。
- 当前只有模拟试用数据，没有真实客户导入执行器；客户资料、岗位 smoke、发布和 UAT 回到受控客户交付证据。
- 角色文档不再登记每个 JSON-RPC、字段、Ent 表、测试数量或环境版本。具体能力状态看[产品能力进度台账](产品能力进度台账.md)，具体实现看代码和测试。

变更角色、流程、模块或字段时，按“领域真源 → 权限码 → usecase → customer config → 页面 / 动作投影 → 测试 → 文档”核对。正文与代码冲突时修正文档，不再创建平行动作矩阵或本地审查报告。
