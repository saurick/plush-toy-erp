# 模块实施治理 / Implementation Governance

- 文档类型：个人 ToB 项目实施规则
- 状态：当前治理规则
- 适用范围：项目负责人使用 Codex 把甲方需求和反馈变成可交付版本
- 不替代：当前代码、schema / migration、测试、目标环境证据和客户验收

## 1. 当前开发模式

本项目不是多人研发组织。甲方主要提出业务目标、现场痛点和使用反馈；项目负责人负责业务沟通、范围和优先级，Codex负责在真实仓库中讨论方案、实现、测试，并在取得明确授权后执行部署。

甲方可能通过其他聊天软件反复校对需求。只有项目负责人带回 Codex 任务并明确说明来源的摘要、截图或资料才进入本轮范围；外部聊天记录、AI 对话和截图本身都不是代码、schema 或产品状态真源。

普通需求按一个循环处理：

1. 说清本次要解决的业务问题、使用岗位和可观察结果。
2. Codex 读取相关代码、schema、测试和正式文档，确认当前真源。
3. 在甲方目标内补齐必要的正确性、异常恢复、权限和基础易用性，形成最小完整实现。
4. 按影响面完成自动化或真实页面验证，准确说明尚未覆盖的环境。
5. 只有取得本轮明确授权后，才部署固定版本并读取目标环境结果。
6. 甲方使用后继续反馈；按缺陷、原需求细化或新需求进入下一次循环。

这六项是一次开发循环，不是要求分六个阶段建文档或等待甲方逐项确认。当前默认只使用 Codex；以后即使增加其他 Agent，也继续遵守同一真源、writer、授权和验证边界，不因 Agent 数量增加流程。

## 2. 甲方、项目负责人和 Codex 各自决定什么

| 责任方 | 主要输入或决定 | 不要求承担 |
| --- | --- | --- |
| 甲方 | 业务目标、现场痛点、岗位责任、财务税务、真实数据口径、不可逆选择、使用反馈和最终业务验收 | 阅读代码、设计技术方案、确认架构层、验证内部键、测试形态或实现步骤 |
| 项目负责人 | 把外部沟通转成明确范围，决定优先级和版本，确认高风险业务选择，授权部署和 Git 动作 | 手工补写完整软件规格或逐项指挥 Codex 的工程实现 |
| Codex | 核对真源、提出简单方案、补齐工程闭环、实现、测试、说明风险和目标环境边界 | 把自己的推断冒充甲方要求，或替甲方决定真实业务责任与合规承诺 |

甲方没有覆盖完整逻辑很正常。能从现有系统、业务正确性和低风险默认中安全决定的内容，由项目负责人和 Codex 主动闭环；只有岗位审批、财务税务、真实数据隔离、不可逆动作、合同或合规承诺等选择需要甲方确认。等待这类决定时，只暂停对应分支，不冻结整个模块。

面向甲方只沟通：本版解决什么、在哪个固定版本、是否已发布、怎么使用、有什么已知边界、反馈如何处理。产品状态、架构责任、验证内部键和测试类型是内部研发证据，不是甲方逐级验收流程。

## 3. 最小完整与复杂度边界

“最小”表示不为未来可能需求预造通用引擎、配置层、状态、后台任务或兼容分支；“完整”表示当前承诺范围内不能留下错账、越权、残值、悬空状态或无法恢复的缺口。

Codex 只检查与本次改动有关的内容：

- 真源：复用现有字段、表、usecase 和组件，不从页面或 Workflow payload 补造事实。
- 生命周期：正常、重复、非法、取消 / 冲正和失败恢复与动作风险相称。
- 权限：后端 RBAC 和业务责任守住敏感动作；前端隐藏不是安全边界。
- 字段链路：来源切换、清空、编辑、列表、详情、打印和导出不产生残值或缺值。
- 使用体验：岗位人员能理解，默认态、交互态、恢复态和错误态可用。
- 验证：只运行能证明本次承诺的检查，不用全量绿色掩盖业务或目标环境缺口。

新增抽象、中间层、表 / 字段、状态、配置、fallback、双写或后台任务前，必须能回答：现有能力为什么不足、最简单替代方案是什么、新复杂度由哪条当前需求或正确性要求承担。回答不了就不增加。

## 4. 什么时候使用专项治理

| 变化 | 处理方式 |
| --- | --- |
| 复用既有字段、接口和页面合同的普通修复 | 直接修改并做受影响验证 |
| schema、migration、Source Document、Fact、Workflow、RBAC 或跨模块字段真源 | 使用 `$plush-domain-boundary-governance` |
| 页面结构、交互或岗位语言明显变化 | 使用 `$plush-page-design-governance` 并验证真实页面 |
| seed、fixture、客户数据导入或清理 | 使用 `$plush-seed-import-governance`；模拟数据不冒充真实数据 |
| migration apply、部署、备份恢复、回滚或目标环境排障 | 使用 `$plush-operations-governance`，绑定固定版本和目标证据 |
| 需要选择测试范围或解释绿色结果 | 使用 `$plush-test-governance`，按影响面选择，不机械跑全站 |

专项治理只服务当前风险，不要求把一个需求拆成 docs、schema、repo、API、UI 等多个独立项目，也不要求普通任务遍历所有治理文档。

## 5. 版本状态与反馈

| 状态 | 只表示 |
| --- | --- |
| 本地完成 | 约定功能和必要工程闭环已实现，并完成相应本地验证 |
| 已发布 | 固定版本已在目标环境完成 migration、配置、健康检查和必要 smoke |
| 使用中 | 甲方已开始在约定范围使用，问题继续按反馈修正 |
| 已验收 | 存在明确业务验收或签收记录 |

后续反馈按实际影响分类：

- 不符合本版承诺、导致错账、越权、无法恢复或主路径阻断：缺陷修复。
- 原目标在使用中需要调整但不改变核心业务责任：原需求细化或小版本优化。
- 新流程、新报表、新自动化或新的客户口径：新需求。

反馈不会让旧版本变成“从未完成”，也不能用本地实现、历史发布或自动化绿色代替当前目标环境和业务验收。

## 6. 收口方式

普通任务最终只需说明：实际完成内容、Codex主动补齐的必要闭环、修改范围、验证结果、未执行的部署 / 真实数据 / 客户验收，以及反馈进入下一轮的方式。

不为普通任务另建需求编号、阶段台账、审批记录、架构图或独立评审报告。当前实现看[当前真源与交接顺序](../当前真源与交接顺序.md)，产品能力状态看[产品能力进度台账](产品能力进度台账.md)，长期方向看[产品完成路线图](产品完成路线图.md)。
