# 岗位任务中心 v2 / Mobile Role Tasks v2

结论：这是岗位任务端当前 **Current** 选中任务流程，但不是整页替换：保留 v1 的待办 / 已办 / 提醒 / 我的列表、筛选和分页，选中任务后进入 v2“查看任务 → 处理任务 → 可信结果回执”，结束后恢复原列表状态。v1 列表基线与 v2 选中任务流程共同组成当前移动任务主路径。

## 单一任务

岗位人员在手机上完成一件事：从任务列表找到当前事项，核对信息；有多种处理方式时明确选择动作，只有一种动作时直接填写所需信息，确认后得到可追溯回执。

组合主路径固定为：

1. v1 任务列表：保留现有标签、筛选、分页 / 分批展开和任务卡片。
2. v2 全屏查看任务：核对任务、来源、权限、真实风险和 ProcessRuntime 执行轨迹。
3. v2 全屏处理任务：只显示服务端允许的动作和对应输入。
4. v2 全屏结果回执：只展示可信提交结果，并可恢复原列表状态。

详情与处理步骤可按当前权限直接点击切换；结果步骤只有在已有已确认回执或“提交结果待确认”记录时才开放。没有回执时不能进入空结果页，用户需先在处理步骤完成一次有效提交。`催办` 只属于第 2 步里的处理动作，不再充当“打开处理页”的隐含入口。

## 重新设计的关键决策

| 问题                                 | v2 决策                                                                                                                                                                                                                             |
| ------------------------------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 点击催办才像是进入下一步             | 三个步骤使用真实按钮；详情、处理按权限直接导航，结果只在已有确认回执或待确认记录时开放。                                                                                                                                            |
| 详情、动作输入与结果挤在同一长页面   | 拆成三个全屏任务阶段，每屏只完成一个判断。                                                                                                                                                                                          |
| 三个步骤反复展示同一任务信息         | 三步条只保留步骤名；详情页集中展示状态、责任岗位和截止时间，处理页与回执页只保留防止办错任务所需的任务名和来源。                                                                                                                    |
| 详情字段大量拼接空值与通用任务元数据 | “业务信息”只逐项展示有值的客户、款式、物料、数量、金额等业务字段；状态、责任岗位和截止时间不再在字段卡中重复。                                                                                                                      |
| 催办与流程导航混在一起               | 催办与完成、阻塞、退回、解除阻塞同属“处理动作”；没有额外导航权限。                                                                                                                                                                  |
| 无权限时只能看见禁用按钮             | 仅催办任务显示非交互的“本次操作：催办”摘要并直接填写原因，不伪装成可选择按钮；只读任务显示原因和已有回执，不展示假动作。                                                                                                            |
| 选择与执行容易混为一谈               | 只有多种处理方式时使用原生单选框；卡片内标题和说明负责建立选择语境，底部“确认催办”等按钮才是真正执行命令。                                                                                                                          |
| 提交后缺少闭环反馈                   | 提交后进入结果回执，明确成功、待确认、任务、来源、动作、当前状态和说明；历史处理线索只读保留，原型不补造处理人或时间。                                                                                                              |
| 业务轨迹只有长文本                   | 详情和已确认回执复用“执行轨迹”，只显示已执行、当前、受阻和本任务锚点；等待节点不冒充确定的未来步骤。                                                                                                                                |
| 回执重复开发者说明和返回入口         | 结果页只保留办理结果、任务身份、动作、状态和用户填写内容；步骤条负责回看任务，底部只保留结果确认和返回列表，不重复“查看任务”或内部边界说明。                                                                                        |
| 列表与深层处理的职责容易混淆         | 保留 v1 的四项主导航、筛选和分页交互；无审批权限时显示“全部 / 风险 / 超时”，有审批权限时在同一行显示“全部 / 审批 / 风险 / 超时”。`todo / approval / risk / history` 仍是各自服务端查询视图，v2 只承接选中任务后的查看、处理与回执。 |
| “我负责”与“全部”高度重复             | 删除只按已加载 `todo` 和岗位池做客户端近似计算的“我负责”；如未来需要完整个人队列，应由独立服务端 assignee 视图提供游标与数量。                                                                                                      |
| 列表顶部优先提示与筛选重复           | 删除独立“优先事项”提示条；待办页的已加载任务分布说明当前加载池构成，筛选和任务卡直接承接下一步操作；已办页直接进入结果列表，不重复整池分布。                                                                                        |
| 长文本、键盘、暗色和窄屏容易失控     | 文本允许自然换行；内容区独立滚动；底部动作区固定；适配 390 / 430、暗色和移动键盘。                                                                                                                                                  |

视觉方向采用成熟企业移动工作台常见的克制模式：单列任务队列、低装饰层级、语义色只表达风险或结果、44px 以上触控目标、固定主动作和可见焦点；不复制任何外部产品的品牌或业务结构。

## 可评审状态

列表中四条样本分别承担不同的回归职责：

| 样本                 | 进入详情        | 第 2 步                                                            | 第 3 步                        |
| -------------------- | --------------- | ------------------------------------------------------------------ | ------------------------------ |
| 确认来料存放位置     | 可处理          | 完成 / 阻塞 / 退回 / 催办；覆盖必填校验和提交                      | 提交前不可进入 -> 提交成功回执 |
| 等待成品质检结论     | 仅可催办        | 显示非交互的“本次操作：催办”，直接填写催办原因，不允许代替品质完成 | 提交前不可进入                 |
| 查看上周成品入库结果 | 只读            | 解释只读原因，无提交按钮                                           | 已确认成功回执                 |
| 多批次混装长文本任务 | 可处理 + 长文本 | 长标题、长来源、长说明、长输入                                     | 结果待确认 -> 刷新确认恢复路径 |

处理校验保持当前项目语义：

- `完成`：完成反馈必填；处理页不再重复收集附件编号、链接或自由文本“证据”。
- `阻塞 / 退回 / 解除阻塞 / 催办`：对应原因必填；催办不开放附件上传。
- 照片、异常截图和处理凭证统一通过任务摘要内的附件次要动作按权限查看或管理，不再占用独立大卡片；旧 `evidence_refs` 仅作为“历史处理线索”只读显示。
- 校验失败时定位并聚焦第一个错误字段；提交时禁用重复动作。
- `Ctrl/Cmd + Enter` 可提交；`Escape` 返回详情；触屏和浏览器 / 系统返回都不丢失当前草稿。
- 使用 `visualViewport` 收敛软键盘出现后的可视高度，输入框聚焦时滚动到可见区域。

## 业务与权限边界

- 原型只表达页面骨架、信息层级、导航、处理表单和反馈状态，不新增 API、RBAC、菜单、路由、schema、migration 或客户专属逻辑。
- 列表中的 `todo / approval / risk / history` 是四类服务端查询视图的交互表达；`approval` 只在当前账号具备任一有效审批能力时作为同一筛选分段行中的“审批”显示，不使用独立全宽卡片，也不扩成第五个底部主导航。正式运行时继续使用各自游标、快照与分页结果，不在前端把四类数据重新拼成第二套任务真源。
- 可见不等于可处理。仅催办和只读样本用于评审 `canOperateTask` / `canUrgeTask` 的页面投影，不是新的权限真源。
- 催办权不等于附件写入权。附件上传继续要求 `workflow.task.update` 和服务端 owner / assignee 范围；无上传权时不显示假“选择附件”控件。
- Workflow task 的完成、阻塞、退回、解除阻塞或催办只更新协同任务，不等于库存、出货、质检、应收、应付、开票或付款事实过账。
- `get_task_process_context` 只能证明持久化节点的已执行 / 当前 / 受阻状态、本任务锚点、attempt 和 outcome。`waiting` 可能属于未选分支，Current 界面不得把它排成必经的未来 stepper。
- 移动端把 ProcessRuntime “业务轨迹”和 `list_task_events` “本任务处理记录”分开显示；责任岗位、状态和截止时间集中放在任务摘要，处理记录只保留真实事件与意见，不重复责任摘要，也不代替领域 Fact。
- 主来源在任务摘要中显示业务类型与可读单号；只有额外相关单据存在时才显示“相关单据”，不把主来源复制成第二张卡，也不暴露内部主键、权限 key、API 名称或开发者字段。
- 详情中的处理提示是只读的原型规则示例，不是人工输入内容。正式运行时应由任务状态、当前账号可用操作和来源入口共同派生；来源入口还必须通过当前账号的页面权限投影，无法可靠派生时不应使用静态样例兜底。
- 原型数据全部是评审样本，不是 yoyoosun 真实数据或客户确认事实。

## 已吸收切片与待验收差异

本地工作树已把以下内容映射回当前组件、API、权限与回归测试：

1. `MobileRoleTasksPage` 的列表选择与三步 screen state。
2. `MobileTaskDetailScreen` 的全屏详情、单行步骤导航、任务摘要、摘要内的附件次要动作、仅有值的业务信息、权限解释和共享 ProcessRuntime 执行轨迹；附件与历史处理线索分离展示，不再重复主来源、责任摘要、完成反馈或底部返回入口。
3. 独立全屏处理页的精简任务上下文、动作选择、原因 / 反馈草稿保留、字段校验、提交中与重复提交保护；多动作使用原生单选框，单一催办不显示伪选择控件或证据输入，底部只保留本次提交命令。
4. 独立结果回执页的 `confirmed / unknown / failed` 三态、重新确认与恢复入口；提交前不开放空回执页，步骤条负责回看任务，底部不重复“查看任务”；只有 confirmed 且存在正式流程锚点时才重新读取并显示“当前流程”，无流程锚点不渲染空流程卡或开发者边界说明。
5. 390 / 430、暗色、长文本、焦点返回、软键盘和固定动作区浏览器回归。

以下现有能力是 v2 的非回退边界，不因页面结构调整而删除或用静态样例替代：

- 客户运行态 guard、岗位权限与 action explain 仍在进入列表和提交动作前生效；失败时保持 fail closed。
- `todo / approval / risk / history` 各自保留服务端游标分页、快照一致性、空态、失败重试与过期请求保护。列表只显示一个“显示更多”入口：优先展开已加载内容，耗尽后按同一快照续取下一页；顶部刷新才重新获取最新快照。
- 任务附件继续使用真实附件组件和上传权限：已有附件显示“附件（N）”，无附件且可上传时显示“添加附件”，无上传权时显示“查看附件”。回执里的动作、状态、原因与历史处理线索只消费后端确认结果或受权限保护的事件投影，不由前端推断处理人或时间。
- 账号信息、切换正式允许的入口和退出登录仍需保留清晰入口；浏览器 / 系统返回、刷新恢复、焦点返回和软键盘可视区都属于正式回归范围。

上述代码吸收已经形成有意的 v1 列表 + v2 选中任务流程，不以“整页切成 v2”为完成条件。Current 只表示当前产品与本地运行态采用该流程；自动化、浏览器验收、发布、目标环境 smoke 和客户 UAT 仍必须分别举证，不能互相替代。

## 人工评审路径

1. 在 390px 和 430px 宽度分别打开 `index.html`，确认页面无横向滚动；再在真实岗位页确认 v1 列表标签、筛选和分页仍可使用。
2. 从列表任务进入详情，确认步骤条没有第二行说明，任务摘要只展示一次状态、责任岗位和截止时间，“业务信息”没有斜杠拼接或 `-` 占位；再确认执行轨迹按服务端顺序显示已执行 / 当前节点、重试次数和“本任务”锚点，附件不再占用独立大卡，而是在摘要内按状态显示“附件（N）”、“添加附件”或“查看附件”。没有额外相关单据时不显示空卡，没有回执的任务第 3 步应禁用。
3. 在可处理任务选择“完成”，空提交应聚焦完成反馈；填写后提交应进入成功回执。
4. 在仅催办任务确认第 2 步不出现“选择处理方式”、可点击的催办选项、证据输入、附件上传或重复“返回详情”，只显示任务上下文、“本次操作：催办”、催办原因与底部“确认催办”；在只读任务确认没有提交按钮。
5. 打开长文本任务的第 3 步，确认底部没有重复“查看任务”，先看到结果待确认，再点击刷新结果确认恢复态。
6. 切换暗色并用 Tab、Shift+Tab、Escape、Ctrl/Cmd+Enter 检查键盘路径与可见焦点，再用浏览器 / 系统返回核对详情和列表的筛选、已加载分页、滚动与焦点恢复。
