# 菜单与正式入口合同 / Menu And Formal Entry Contract

本文说明正式 ERP 入口由谁定义、客户配置怎样收窄、菜单变更要同步什么。它不复制当前全部菜单，也不把候选原型写成已实现能力；具体菜单、路由、权限和页面状态始终以当前代码、active customer revision 和测试为准。

## 当前结论

- Product Core 只维护一套正式入口，不为客户复制菜单代码或业务页面。
- 客户配置可以隐藏、排序、分组、改低风险显示文案和推荐岗位入口，但不能新增后端权限、路由、业务对象或事实能力。
- 页面可见、菜单可点和动作可执行是三件事。任何业务动作仍由服务端 RBAC、模块状态、active revision、来源读取权、责任池、对象状态和领域 usecase 共同校验。
- Workflow / ProcessRuntime 页面只办理协同或已登记的领域命令；任务完成不等于库存、质检、出货或财务事实生效。
- `/__dev/**`、原型、治理、测试和开发文档只属于开发工作台，不进入正式 ERP 菜单。

## 运行时真源

| 层面 | 当前真源 | 职责 |
| --- | --- | --- |
| 默认导航与分组 | `web/src/erp/config/seedData.mjs`、`businessModules.mjs` | 定义 Product Core 的入口、分组、标题和路由 |
| 前端权限投影 | `web/src/erp/config/menuPermissions.mjs` | 从正式导航生成菜单权限分组和角色预设 |
| 后端菜单 | `server/internal/biz/rbac.go` 的 `BuiltinAdminMenus()` | 登录菜单、权限管理选项和后端 required permissions |
| 客户菜单 | `config/customers/<customer-key>/menuConfig.mjs` 与部署注入的 `customer-config.js` | 在 Product Core 上收窄显隐、排序、分组和文案 |
| 最终有效入口 | `customer_config.get_effective_session` 与当前账号 RBAC | 返回当前客户、账号和角色真正可进入的页面与动作 |
| 页面行为 | 当前路由、页面、API client、后端 handler / usecase 和测试 | 决定页面能做什么，菜单不能替代这一层 |

只改其中一层会造成漂移。菜单或路由变化时，必须同时核对前端默认导航、客户配置、后端内置菜单、权限投影、帮助文档和测试。

## 可见与可执行边界

```text
页面可见 = 后端菜单允许
        ∩ Product Core 页面存在
        ∩ active revision 页面投影
        ∩ 当前角色页面投影
        ∩ 模块可读

动作可执行 = 后端 RBAC
          ∩ active revision entitlement
          ∩ 模块可写
          ∩ 来源读取权与数据范围
          ∩ owner / assignee / 责任池
          ∩ 对象状态、版本、幂等和领域规则
```

前端隐藏不是安全边界；super admin 也不能绕过领域状态、事实真源和 active customer revision 的失败关闭规则。

## 入口颗粒度

| 表达位置 | 应表达 | 不应表达 |
| --- | --- | --- |
| 菜单分组 | 稳定业务域，如销售、采购、仓储、生产、财务 | 把多个流程步骤拼成一个长期分组 |
| 菜单入口 | 稳定业务对象或工作台，如销售订单、库存台账、任务看板 | 用入口存在暗示未实现能力已经可用 |
| 页面 Tab / 筛选 | 同一对象的状态视图、队列或只读投影 | 新建第二套状态机或事实判断 |
| 页面动作 | 新建、提交、审批、过账、取消、冲正、打印等真实动作 | 用按钮文案掩盖无来源或无后端闭环 |
| 岗位任务端 | 当前岗位的任务、交接和可恢复办理路径 | 复制整棵桌面菜单树 |

来源生成、事实动作和只读台账的入口规则见[页面来源生成入口规则](页面来源生成入口规则.md)。

## 候选菜单与原型

[产品原型中心](prototypes/README.md)中的菜单覆盖矩阵和正式菜单候选属于“评审与参考”。它们可以帮助检查遗漏、分组和信息密度，但不能反推当前运行时菜单、RBAC、route、schema、migration 或客户配置。

候选入口进入运行时前，至少回答：

1. 它服务哪个岗位和高频任务，是否已有更直接入口。
2. 页面、路由、API、RBAC、模块状态和恢复态是否真实存在。
3. 它是 MasterData、Source Document、Workflow、Fact、Ledger 还是只读报表。
4. 客户配置是收窄已有能力，还是试图创造新的 Product Core 能力。
5. 旧入口是否应直接退出；本项目不为未发布草稿保留兼容别名或重定向。

## 变更与验证

菜单或正式入口变化时按以下顺序收口：

1. 先确认页面职责、字段真源和业务动作已经闭环。
2. 修改前端导航、业务模块和路由。
3. 同步后端内置菜单、required permissions 和客户配置投影。
4. 核对帮助、培训、原型状态和本文件是否仍准确。
5. 覆盖未登录、disabled、无权限、模块关闭、active revision 缺失、多角色账号和直接 URL 访问。
6. 用真实浏览器检查默认态、切换态、无结果、无权限和恢复态；菜单可见性测试不能替代业务动作测试。

最低静态入口：

```bash
node --test web/src/erp/config/seedData.test.mjs web/src/erp/config/menuPermissions.test.mjs
cd server && go test ./internal/biz ./internal/service
```

实际执行范围以[自动化测试策略](自动化测试策略.md)和 `bash scripts/qa/affected.sh --plan` 为准。

## 维护规则

- 本文只维护稳定合同，不登记逐轮菜单改名、路由调整、测试计数或历史实施批次。
- 当前菜单清单从代码和 effective session 读取，不在 Markdown 再抄一份。
- 新增真正的正式入口或改变菜单职责时更新本文；普通页面内部动作或文案修复不机械更新。
- 客户专属菜单差异进入客户配置与对应客户受控文档，不写入 Product Core 默认菜单。
