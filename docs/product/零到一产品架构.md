# 零到一产品架构 / Zero To One Architecture

## 定位

`plush-toy-erp` 的目标是毛绒玩具工厂任务驱动型 ERP 产品内核，而不是一次性外包系统、所有行业通用 ERP、低代码平台或复杂 BPMN 系统。

本文直接定义本项目的产品定位、分层和闭环顺序。当前实现层级仍由代码、测试、[当前真源与交接顺序](../当前真源与交接顺序.md) 和具体任务证据共同确认。

当前路线是：

| 层级 | 口径 |
| --- | --- |
| Product Core | 单一产品内核，沉淀通用 usecase、schema、权限、事实规则和帮助口径 |
| Industry Template | 毛绒玩具及相近轻工行业模板，沉淀默认角色、流程、字段、编号和 seed / import 模板 |
| Customer Config | 客户配置包，承接公司名、logo、菜单、字段、编号、角色、初始化数据和客户打印样本引用 |
| Customer Extension | 极少量客户专属扩展，必须隔离并记录退出条件 |
| Delivery / Ops | 私有化部署、备份恢复、升级、培训、巡检和维护费交付能力 |

打印格式当前不进入 Product Core，也不作为行业模板默认能力。现阶段只记录客户打印样本、字段来源和交付诉求；若后续多个真实客户的同类单据结构高度重复，再单独评审是否做 Print Template Core MVP。

## 传统专业系统能力映射 / Professional System Capability Mapping

`plush-toy-erp` 对外仍是一套毛绒玩具工厂 ERP，内部按业务域和事实责任分层。CRM、PLM、MES、WMS、QMS、BPM 等名称只用于解释本产品覆盖了哪些传统专业能力；这些名称在行业和厂商之间本就存在交叉，不能据此自动创建独立产品、服务、数据库、账号体系或双向同步链路。

下表是多对多的能力对照，不是部署拓扑、代码目录、数据表归属或实现完成度台账：

| 本项目业务域 | 常见专业系统标签 | 本项目当前归属 | 当前不因此宣称 |
| --- | --- | --- | --- |
| 客户、联系人、销售订单、返工回厂 | ERP / CRM | 客户主数据、销售 Source Document 与原出货返工追溯继续由 ERP 客户 / 销售域拥有 | 完整 CRM；线索、商机、营销自动化和呼叫中心不是当前主链 |
| 产品、SKU、BOM、工序 | ERP / PLM / PDM | 产品工程主数据、BOM 版本和源单冻结快照由 ERP 工程域拥有 | 完整 PLM / PDM；CAD、3D、ECN 和设计协作需有真实需求后另评审 |
| 供应商、采购订单、收货与退换 | ERP / SRM / MRP | 供应商主数据、采购承诺、收货、IQC、入库与处置按 Source Document / Fact 分层 | 供应商门户、自动 MRP 或完整供应链协同平台 |
| 生产订单、固定路线、WIP、委外和异常执行 | ERP / MES / APS | 生产承诺、执行批次、逐工序质量门禁和生产事实留在 ERP 生产 / 委外域 | 完整 MES / APS；设备联网、OEE、实时采集和产能优化需另评审 |
| 库存、批次、预留、盘点、调拨与出货 | ERP / WMS / WCS | 库存流水、余额、批次、预留和出货事实由 ERP 库存 / 出货域拥有 | 完整 WMS / WCS；真实库位、波次、自动化立库和设备控制不在当前承诺内 |
| 来料、过程、成品、委外和退货检验 | ERP / MES / QMS | 检验结果和质量处置由独立 Quality Fact 拥有，Workflow 只负责协同 | 通用 QMS / LIMS；实验室、计量校准和法规体系需另评审 |
| 应收、应付、发票、收付款、核销和红冲 | ERP / 财务系统 | 业务财务来源、往来余额和纠错链由 ERP 财务域拥有 | 完整会计系统；银行直连、总账、税控和合并报表不在当前 V1 |
| 审批、岗位任务、异常流转和业务轨迹 | ERP Workflow / BPM | Workflow / ProcessRuntime 统一处理责任、协同和运行轨迹，不拥有领域事实 | 低代码 BPMN 平台，也不表示任务完成即可写库存、质量、出货或财务事实 |
| 看板、审计和外部集成 | ERP / BI / EAI | 派生读模型、运行审计和受控集成继续引用各领域正式真源 | 独立数据仓库、通用 BI 或企业集成平台 |

真正决定实现边界的是 `MasterData → Source Document → Workflow / ProcessRuntime → Fact / Ledger → Derived Read Model` 的责任链，以及 RBAC、Customer Config 和 Delivery / Ops 的独立职责。精确状态和事实边界见[状态、Workflow 与 Fact 边界](../architecture/状态工作流事实边界.md)，当前实现成熟度见[产品能力进度台账](产品能力进度台账.md)；本表不复制这两份真源。

只有在专业深度、实时性、合规性、运行负载或独立团队边界形成真实需求时，才评审把某项能力接入外部专业系统。即使拆分，也必须保持一项数据只有一个权威 owner，通过受控 API、事件或导入合同交互，不建立双方都可改写的第二真源。

## 三阶段路线

| 阶段 | 目标 | 当前动作 |
| --- | --- | --- |
| 第一阶段 | 单客户私有化部署 + 配置预留 | 以 `yoyoosun` 客户为第一个私有化客户实例，建立配置和交付骨架 |
| 第二阶段 | 多客户私有化部署 | 每客户一套数据库 / 对象存储 / env / 初始化数据 / 客户打印样本记录，代码统一 |
| 第三阶段 | SaaS 多租户 | 未来单独评审，不在当前阶段实现 |

当前不实现 SaaS runtime tenant，不新增 `tenant_id`，不改 Ent schema，不改 RBAC 为多租户模型。

## 业务闭环主线

0 到 1 的产品目标不是先做完整 SaaS，也不是先做通用低代码平台，而是把毛绒工厂的业务主链路按事实边界闭环：

| 主线 | 0 到 1 成熟口径 |
| --- | --- |
| Order To Shipment | 客户订单作为 Source Document，老板审批只推进协同；真实出货必须由 ShipmentUsecase 和库存事实确认 |
| Procure To Inventory | 采购承诺、到货、质检、入库、退货和调整分层；采购入库事实写 `inventory_txns / inventory_balances / inventory_lots` |
| Production / Outsourcing | 生产领料、委外发料、委外回货、成品入库必须形成事实，不靠 workflow task done 伪造库存 |
| Shipment To Finance | `shipping_released` 只表示可发货；实际 shipped 后才评审应收、发票、收款和对账 |
| Productization / Delivery | 用一个产品内核、一个行业模板、多个客户配置包和私有化部署包复制客户，不复制多套核心代码 |

## V0 到 V6

| 版本 | 目标 | Definition of Done 摘要 |
| --- | --- | --- |
| V0 | 架构骨架 | 文档、目录、边界和 release gates 建立；不改 runtime |
| V1 | 订单 / 客户 / 产品 / SKU / BOM / Boss Approval | 主数据和源单据边界清楚，老板审批只推进协同和单据阶段 |
| V2 | 采购 / 来料 / 质检 / 库存 | 采购、质检、库存事实 usecase 分层，库存流水可追溯 |
| V3 | 生产 / 委外 / 成品入库 | 生产和委外源单据、成品入库事实、库存过账边界清楚 |
| V4 | 出货放行 / 出货事实 / 预留 / 实际出库 | `shipping_released` 与 `shipped` 分离，出货事实和库存扣减由 ShipmentUsecase 落账 |
| V5 | 财务对账 / 应收 / 应付 / 发票 / 收付款 | 财务事实在真实 shipped、receipt、invoice、payment 后形成 |
| V6 | 产品化交付 / 配置包 / 部署包 / 培训 / 运维 | 私有化交付包、升级说明、培训和维护费支持闭环 |

## 当前 V0 边界

- 只做文档和目录骨架。
- 不迁移旧代码。
- 不接前端 docs registry。
- 不新增 schema、migration 或 runtime loader。
- 不把当前甲方资料升级为 Product Core 规则。
- 不把仓库外输入材料作为 runtime source of truth。
