# 业务公式与计算口径 / Business Formula and Calculation Policy

本文集中回答“这个数量、金额、余额或重量是怎么算的、由谁算、什么时候冻结、页面预览能不能当真源”。它是当前业务公式的阅读索引，不建立第二套运行真源；若本文与当前 schema、领域代码、事务校验或测试不一致，以 [当前真源与交接顺序](../当前真源与交接顺序.md) 定义的真源层级为准，并把本文视为需要修正的文档缺陷。

本文只证明当前 Product Core 代码口径，不证明任一目标数据库已完成 migration、目标环境已部署、岗位 smoke 已通过或客户已验收。本文括号中的 `Fxx` 是公式编号，`Pxx` 是页面预览编号；它们与客户文档中的同号流程编号不是同一对象，正文引用时必须同时写出规则名称和编号类型。

## 先看结论 / Decision Rules

| 标记 | 含义 | 能否作为保存、过账或对账依据 |
| --- | --- | --- |
| `Current · Formal` | 服务端 Decimal 计算、事务内校验、冻结快照或正式读模型 | 可以；写路径仍须以服务端重读和事务结果为准 |
| `Current · Preview` | 前端按当前响应做精确预览、建议值或一致性校验 | 不可以；来源可能变化，服务端必须重算 |
| `Current · Print Draft` | 只作用于当前打印弹窗草稿和纸面 DOM | 不可以；不反写 Source Document、Fact 或 Ledger |
| `Current implementation · Pending` | 当前代码行为明确，但业务政策、异常数据策略或舍入口径尚未完全冻结 | 只能描述当前行为，不应扩写成长期产品承诺 |
| `Not Implemented` | 当前没有正式公式，或只有人工录入 / 快照字段 | 不得从名称、历史文档或页面文案补造 |

使用这些公式时还要遵守四条边界：

1. 状态集合是公式的一部分。例如采购草稿会占用建单余量，销售出货余量只统计 `SALES_DELIVERY + SHIPPED`，返工回厂容量统计 `DRAFT / RECEIVED`；不能统一简化成“计划量减已用量”。
2. 计算粒度是公式的一部分。库存公式必须在主体、产品 SKU、仓库、单位和批次完全一致的粒度内成立，不能跨粒度借量。
3. Workflow 或 ProcessRuntime 只负责协同与门禁。`task done`、审批通过或 `shipping_released` 都不能直接代入库存、出货、财务或质量事实公式。
4. 页面合计、来源候选和打印金额都是派生结果。它们不能覆盖服务端 Source Document、Fact、Ledger 或冻结快照。

## 通用数值与舍入 / Numeric And Rounding

| 规则 | 当前口径 | 真源 |
| --- | --- | --- |
| 服务端存储 | 本文涉及的数量、金额和比例字段通常使用 PostgreSQL `numeric(20,6)`；具体字段仍逐项回到 Ent schema 核对。SQLite 的 `numeric` 声明不能单独证明 PostgreSQL 六位精度。 | [decimal.go](../../server/internal/data/model/schema/decimal.go) |
| JSON-RPC | 业务十进制数使用普通十进制字符串传输，不使用 JSON number、指数形式或超过字段精度的文本。 | [jsonrpc_params.go](../../server/internal/service/jsonrpc_params.go) |
| 服务端计算 | 正式乘除使用 `shopspring/decimal`。本文的 `Round6(x)` 表示在该公式明确的位置四舍五入至 6 位小数。 | 各公式列出的 biz / repo 实现 |
| 前端正式预览 | 非负 `numeric(20,6)` 预览使用十进制定点字符串或 BigInt，范围为 `0` 至 `99999999999999.999999`，不经过浮点 `Number`。 | [numeric20Scale6.mjs](../../web/src/erp/utils/numeric20Scale6.mjs) |
| 打印草稿 | 采购合同和加工合同当前使用 JS `Number` 与两位金额展示规则，只服务纸面草稿。 | [打印模板字段与编辑行为清单](../打印模板字段与编辑行为清单.md) |

不能把“字段最多存 6 位小数”写成“所有公式都在计算点统一 `Round6`”。下面只有明确标注 `Round6` 的公式在代码中显式舍入；其余加减或乘除保持当前 Decimal 行为，最终还受目标 PostgreSQL 字段精度约束。

采购订单页面的现有草稿预览是一个已知局限：

```text
前端当前已占用量 = Σ所有非 CANCELLED 收货单的原始明细数量
前端当前剩余量 = max(采购数量 − 前端当前已占用量, 0)
```

这套预览未纳入已过账数量调整，调整发生后可能与采购收货余量公式（F02）不一致。因此 [purchaseOrderInboundPreview.mjs](../../web/src/erp/utils/purchaseOrderInboundPreview.mjs) 只能标为 `Current · Preview`；服务端返回、建单和过账事务才是正式口径。

### 出货总净重

正式计算分两步：

```text
行原始净重 = 出货数量 × 已解析单位净重（克）
出货总净重 = Round6(Σ行原始净重)
```

## Workflow 岗位任务数量守恒 / Role Task Count Conservation

岗位任务数量是 `workflow_tasks` 的权威读投影，不是浏览器当前已加载数组的长度。当前四个互斥状态及页面口径如下：

| 规则（内部编号） | 标记 | 公式 | 范围与显示边界 | 实现与测试 |
| --- | --- | --- | --- | --- |
| 待办数量守恒（任务数量规则 W01） | `Current · Formal` | `todo = ready + blocked` | 待办页“全部”只表示当前岗位待办集合；`ready` 显示为“待处理”，`blocked` 显示为“卡住”。 | [workflow_role_task_view.go](../../server/internal/biz/workflow_role_task_view.go) / [workflow_role_task_view_repo_test.go](../../server/internal/data/workflow_role_task_view_repo_test.go) |
| 已办数量守恒（任务数量规则 W02） | `Current · Formal` | `history = done + rejected` | 已办页数量使用完整终态集合；“完成”不能吞掉“已退回”。 | [workflow_role_task_view_repo.go](../../server/internal/data/workflow_role_task_view_repo.go) / [jsonrpc_workflow_task_revision_visibility_test.go](../../server/internal/service/jsonrpc_workflow_task_revision_visibility_test.go) |
| 任务总数守恒（任务数量规则 W03） | `Current · Formal` | `total = todo + history = ready + blocked + done + rejected` | “当前岗位任务状态”的总数按四个互斥状态守恒；任何负数或公式不成立的成功响应都失败关闭。 | [workflowApi.mjs](../../web/src/erp/api/workflowApi.mjs) / [workflowApi.test.mjs](../../web/src/erp/api/workflowApi.test.mjs) |
| 风险关注面约束（任务数量规则 W04） | `Current · Formal` | `overdue <= risk`；`approval`、`risk`、`overdue` 不参与 `total` 相加 | 三项是可重叠关注面，同一任务可以既待审批、又有风险、又已超时。账号具备有效 `workflow.task.supervise` 时，风险口径为 `risk_scope=supervised`，页面显示“跨岗风险”，其数量可以大于当前岗位 `total`；否则为 `risk_scope=role`。 | [jsonrpc_workflow_task.go](../../server/internal/service/jsonrpc_workflow_task.go) / [MobileTaskListScreen.jsx](../../web/src/erp/mobile/components/MobileTaskListScreen.jsx) |

首次无游标 `list_role_tasks` 在同一个 PostgreSQL `REPEATABLE READ READ ONLY` 事务中读取数量和首屏行，并返回精确的十项 `counts`、`risk_scope` 与 `server_time`。后续游标绑定 RPC 方法、岗位、视图、风险范围、时间快照、预期总数和累计已见数；跨岗位、跨视图、权限变化、重复 ID、单页超过 `limit` 或普通数量漂移都要求用户重新加载。前端为 `todo / approval / risk / history` 每个槽位分别保存首屏数量快照，任务变更后全部失效并重读；超时判定使用对应槽位的服务端时间，不使用客户端时钟。

这不是严格 MVCC 长会话：游标页之间不会长期占用数据库事务，集合发生“删一条同时增一条”的等数量替换时仍可能逃过数量漂移检测。为这种低概率并发建立投影 revision、物化 ID 集或长事务会显著增加写放大和运行复杂度，当前不实现；遇到任务列表已更新或人工核对存疑时以刷新后的新首屏为准。

## 打印草稿公式 / Print Draft

采购合同和加工合同的金额规则只作用于当前弹窗草稿，符合 [打印模板字段与编辑行为清单](../打印模板字段与编辑行为清单.md) 的“不静默回写业务真源”边界。

| 规则（内部编号） | 标记 | 公式与显示 | 当前限制 | 实现与测试 |
| --- | --- | --- | --- | --- |
| 采购合同打印草稿（打印草稿规则 D01） | `Current · Print Draft` | 采购合同：`默认行金额 = 数量 × 单价`；`数量合计 = Σ可见数量单元格`；`金额合计 = Σ可见金额单元格`。金额显示两位小数，手工金额可覆盖默认值。 | 使用 JS `Number`；数量和单价格式最多 3 位小数。合并区隐藏重复格不参与合计。结果不写采购订单、采购应付或财务事实。 | [materialPurchaseContractEditor.mjs](../../web/src/erp/utils/materialPurchaseContractEditor.mjs) / [materialPurchaseContractEditor.test.mjs](../../web/src/erp/utils/materialPurchaseContractEditor.test.mjs) |
| 加工合同打印草稿（打印草稿规则 D02） | `Current · Print Draft` | 加工合同：`默认行金额 = 数量 × 单价`；数量 / 金额合计只统计可见单元格。金额为空或仍等于旧自动值时，数量 / 单价变化可自动重算；已手改金额保持。 | 使用 JS `Number`；数量最多 3 位、金额最多 2 位且不强制补零。结果不写委外订单、委外回货或应付事实。 | [processingContractTemplate.mjs](../../web/src/erp/data/processingContractTemplate.mjs) / [processingContractTemplate.test.mjs](../../web/src/erp/data/processingContractTemplate.test.mjs) |

打印草稿允许人工修订金额，是为了纸面编辑，不是正式订单金额的 override。若要把打印金额用于业务或财务，必须先建立服务端 view model、Decimal 计算、来源快照和事务校验，不能直接复用这两套 `Number` 规则。

## 已知待收口项 / Known Gaps

1. 采购入库页面草稿预览未纳入已过账数量调整；正式口径已由采购收货余量公式（F02）的服务端事务守住，但页面可能显示过时余量。
2. 采购应付和委外应付没有统一的显式 `Round6`；SQLite 绿色不能证明 PostgreSQL 写入后的舍入政策。
3. 异常历史销售订单若同时存在不一致的金额与单价，出货单价快照和金额快照当前可能采用不同基准；正常订单主路径已校验一致性，但异常数据策略仍待确认。
4. 采购退货当前不会重开采购订单收货容量；是否长期保持，需要在采购履约政策评审后决定。
5. 自动净重不完整时可保留人工整单净重；人工 fallback 的权威层级、核对动作和打印标识仍待业务确认。
6. 采购合同和加工合同打印草稿使用 JS `Number` 与手工金额，不具备订单 Decimal 金额的权威性。
7. 工程打印“总用量含损耗”只有快照，没有独立计算合同；看板也没有业务比例指标。

这些待收口项不是页面用宽松 fallback 自行修正的授权。需要改变行为时，应从领域合同、服务端实现和测试开始，再同步前端预览与本文。

## 变更与验证规则 / Maintenance

修改或新增业务公式时，按以下顺序收口：

1. 明确对象、输入字段、状态集合、计算粒度、舍入点、空值 / 负值 / 溢出规则，以及结果是持久化事实、冻结快照还是读模型。
2. 在服务端领域或数据事务层实现唯一正式规则；页面只做同口径预览和响应校验，不双写或补造事实。
3. 测试至少覆盖正常值、六位边界、舍入边界、零 / 空值、超量或负数、状态释放、并发重验和历史异常策略中适用的部分。没有显式舍入的乘除公式要补 PostgreSQL 写入 / 读回证据。
4. 同步表单、列表、详情、导出和打印消费者；来源切换、取消、冲正、调整后检查残值和缺值。
5. 更新本文、相关领域专题、`docs/product/README.md`、`docs/文档清单.md` 和 `progress.md`；能力实现层级变化时再同步能力台账与客户交付矩阵。
