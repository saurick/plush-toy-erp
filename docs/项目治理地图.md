# 项目治理地图 / Project Governance Map

遇到改动时，先从“常见任务分流”选择最接近的一项，直接确认先看什么、同时检查什么、最容易误判什么。只有需要解释内部层级和完整关系时，再看后面的治理维度与关系图。

本文不是规则全集、roadmap、能力台账、测试报告或运行时真源；强规则回 [AGENTS.md](../AGENTS.md)，当前状态回 [当前真源与交接顺序](当前真源与交接顺序.md)，真实行为回当前代码、migration 和测试。本地开发态可用 [改动规则助手（`/__dev/governance`）](../web/README.md#前端文档入口边界) 只读浏览本文，不新增第二套治理规则。

## 个人 ToB 交付循环 / Personal ToB Delivery Loop

甲方只确认业务目标、关键选择和实际使用结果，不跟随代码实现、内部层级或测试内部键逐级签认；项目负责人和 Codex 负责把输入补成最小充分闭环。详细边界见 [AGENTS.md：个人开发方式与工作区](../AGENTS.md#个人开发方式与工作区) 和 [模块实施治理：当前开发模式](product/模块实施治理.md#1-当前开发模式)。

| 步骤                     | 谁负责                    | 本步完成标志                                                                       |
| ------------------------ | ------------------------- | ---------------------------------------------------------------------------------- |
| 甲方提出目标或痛点       | 甲方                      | 说明业务目标、痛点或使用反馈；无需提供代码方案。                                   |
| 负责人带回 Codex         | 项目负责人                | 标明甲方输入和必要材料，界定本轮可验证业务切片。                                   |
| Codex 补齐并实现最小闭环 | Codex                     | 补齐必要真源、状态、权限、异常、恢复、测试和基础易用性，只采用当前需求所需复杂度。 |
| 明确授权后发布固定版本   | 项目负责人 + Codex        | 确认版本、目标环境、回滚点和发布证据；未获授权不部署。                             |
| 甲方使用反馈后再迭代     | 甲方 + 项目负责人 + Codex | 按实际使用结果归类为缺陷、细化或新需求，进入下一轮。                               |

## 维护规则 / Maintenance Rules

- 本文只维护任务分流、治理维度与口径；完整规则继续留在 `AGENTS.md`、专题文档、skill、hook、QA 脚本或测试策略中。
- 页面默认只展示任务分流中的“你这次准备做什么、先看、同时检查、不要误判”；内部范围、治理维度、交付循环和完整关系图按需展开。
- 新增任务行时必须提供唯一“页面键（内部）”，并写清先看、同时检查和不要误判；页面不得再用关键词或共享路径猜测任务关系。
- 新增“层级 / 状态 / 形态”口径时，先判断是否已有专题真源；若只是已有真源的别名，更新本文链接，不新增第二套定义。
- 新增长期维护 Markdown、重命名文档或改变文档职责时，同步检查 [docs Guide](README.md)、[文档清单](文档清单.md)、最近目录 README、正文引用和 `web/src/dev-workbench/config/devDocs.mjs`。
- 文档中可以使用表格、Mermaid 和指定章节链接降低阅读成本；不要为了形式整齐把长规则、复杂流程或完整测试策略强行塞进表格。
- 只有命中 `AGENTS.md` 的过程记录条件时才更新 `progress.md`；普通且已闭环的小改动不重复留痕。
