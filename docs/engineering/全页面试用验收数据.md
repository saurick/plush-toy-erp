# 全页面试用验收数据 / Trial Acceptance Dataset

本专题适用于准备模拟数据及进行岗位验收。按目标和规模选择配方，再核对生成、执行、读回与清理条件。命令从仓库根目录执行，各环境和入口另有说明。

<a id="seed-business-values"></a>

## 造数的业务字段和值

已有业务记录通过迁移 `20261021134135` 清理，执行前核对 [标记清理预检](../../scripts/qa/business-data-markers-preflight.sql) 与共享开发库的备份恢复升级预演；实际 apply 仍走现有迁移确认入口。

所有 seed、fixture 和试用造数写入普通业务对象时，使用正式字段和自然业务值。名称、标题、备注、原因、地址、检验项及复制/打印/导出内容中，禁止加“模拟、演示、示例、样例、测试数据”等性质说明；页面不显示对应标签或分类。

业务 payload 和客户/供应商/合同快照不得增加 `simulated_only`、`real_customer_data`、`trial_task`、`evidence_class`、`proves_process_runtime`、`acceptance_scenario_key` 等造数标记，也不得用验收批次冒充来源单据。有实际来源时填正式类型、ID 和单号；独立任务不填来源，显示“未关联业务单据”。不为满足造数而伪造流程锚点、岗位权限或业务事实。

造数用途、环境、批次、场景映射、清理范围和证据分类保存在工具计划/回执中，通过既有业务编号、对象 ID 与目标身份精确读回。禁止靠业务字段里的性质标记识别或清理数据；历史审计与幂等回执保留原始事实，存量业务记录按前向迁移清理。

运行时校验复用 `seed-business-values.mjs` 与服务端 `ValidateSeedBusinessText / ValidateSeedBusinessValues`，现有 `test-data-isolation-boundary` 阻止登记造数入口重新写入专用标记。数据来源与证据边界仍由工具回执证明，正常页面值不构成真实客户导入或客户验收证据。

## 数据合同与规模选择

当前唯一整批合同是 `2026.11.07-v9 / 20261107-V9`。本地隔离库和 `demo-133` 使用同一套业务含义、数量与状态矩阵，但数据库 ID 各自独立，不能复制表行或用“编号相同”代替读回证明。正式部署默认不执行这套数据；`customer-test-133` 是甲方测试/验收环境，禁止重放整批合同，只允许在明确授权、exact release / migration 和写后读回下复用 core allowlist 准备 8 个单位与 4 个仓库。

整批入口的 `--source-scale-profile acceptance|volume` 选择来源数据规模，配方统一登记在 `manual-acceptance-source-data.mjs`。完整验收默认 `acceptance`；长期 `scenario-demo` 默认 `volume`，本地与 demo 对账时须选择同档并核对计划摘要。规模只增加主数据、来源单据与明细，现有岗位、事实、异常处理和页面合同继续完整执行。

| 来源数据 | `acceptance` | `volume` |
| --- | ---: | ---: |
| 客户 / 供应商 | 各 60 | 各 180 |
| 材料 | 80 | 240 |
| 产品 / SKU | 20 / 60 | 160 / 480 |
| 工序 | 30 | 60 |
| 销售 / 采购 / 委外订单 | 各 45 | 各 450 |
| BOM 版本 | 45 | 450 |

两档均执行完整事实配方：54 条基础到货样例之外，另建 9 条未入库到货草稿，通过正式质检纠正接口形成待复检、复检合格和复检不合格的独立记录。采购阶段至少读回 63 条到货单和 75 条来料检验记录；纠正前的单号、判定、检查项和原因保持原样；seed 重放与只读核对显式读取已被替代的原记录，浏览器核对在“记录范围”选择“含已替代记录”，并核对撤销判定的操作者、时间、原因及新复检的来源关联。这些样例不参与原有采购拒收处置和库存过账；复检本身不产生库存或财务事实。重复执行复用同一原单与复检单，只读验证不调用写接口。

规模档参与计划和数据摘要，执行器必须采用同一配方。已有同编号数据必须通过精确读回，不按新规模覆盖旧关系；需要丢弃旧演示数据时，先完成独立、可恢复的 demo 数据库重建，再用当前回执执行 fresh apply。不能通过删除本地报告冒充新空库，也不为扩容改变业务含义或伪造事实。

独立 source 入口同样先核对当前批次报告中的目标、规模和语义。新批次在只读确认各类来源对象为空后，先原子保存准备回执，再执行正式业务写入；同档中断可凭此回执继续精确读回。已有同前缀对象而缺少报告时停止，避免先补写部分主数据才发现批次不匹配。

## 可视化增量与正式来源

`visualization-demo-data.mjs` 是 `scenario-demo` 上的本地开发增量，不是新的整批合同、UAT 或客户真实数据。它使用按日期固定的 `VIS-*` 编号，通过销售、采购、生产、工序、财务、库存和 Workflow 正式读写接口 exact-create-or-readback；不直写数据库，也不在前端保存 fixture。

脚本补齐 5 种交期 / 到货风险、6 种生产排期样本及一个五产品完整路线样本，并要求现有财务应收应付、跨仓库存和 PMC 排产任务达到实时读回门槛。已下达的生产与工序事实按业务生命周期保留，退出时按批次编号查找和停用 / 取消可编辑源单，不做物理删除或数据库重置。

## 岗位分工、工程资料与附件

出货手测数据由事实阶段补齐：在同一批次新增四张三行销售订单，经工程核对、裁片委外、工序、质检、成品入库与包装后留足各行出货数量。另留缺货、质检冻结、其他订单占用各一单；本订单行自己的预留可随出货消耗。回执 `shipmentCoverage` 提供订单、SKU、成品仓、批次、入库单和数量；已手测出货的批次按事实读回，不重复补货。

已有同一目标的当前来源报告与采购入库时，可用现有事实入口单独补齐这组订单；目标确认和账号仍按下方整批合同传入：

```bash
node scripts/qa/manual-acceptance-fact-data.mjs --phase shipment-coverage --source-report <同目标的来源报告> --apply
node scripts/qa/manual-acceptance-fact-data.mjs --phase shipment-coverage --source-report <同目标的来源报告> --verify
```

样本按单号复用，档案只补空值，已保存的订单与出货快照不回写。如果手测已把待办或核销状态推进，读回会指出当前样本与原办理起点的差别。早期无来源工作台样本按已有任务退出流程结束，终态仍可从全部任务查看。海关编码沿用产品档案测试样例，仅用于表单展示。

加工合同由独立的 `demo_finance_purchase / uat_finance_purchase` 双岗位模拟账号办理，纯财务账号保持原有权限；收货与工序回货由仓库、工序执行由生产、包装版本确认由业务账号办理。整批事实报告额外读回材料和成品入库的来源待办，核对关联、仓库责任、状态与跳转入口。

旧批次来源单、已过账事实及审计保留；标准路线绑定只通过既有受控替换流程从精确登记的上一批次转移。

客户配置 revision 从完整 manifest 内容生成，独立于模拟数据批次；`customerTrial133` 只登记目标和最低 migration，配置身份由 `manual-acceptance-target-policy.mjs` 从当前受控配置包生成。启动核对已激活记录的用途、目标、product / dataset 配对及环境开关，不维护人工“当前 / 上一版”窗口。

新发布仍要求内容 revision、当前登记数据集和正式配置接口；历史不可变记录只作为原始事实保留，不改写成新身份。详见[版本边界](跨层公共契约与生成规范.md#版本边界--version-boundaries)。

造数读回的“已验证流程实例”按任务阶段正式流程证据中的实例 ID 去重统计；覆盖岗位数和展示用任务数不计入该值。同批续跑仍从已校验摘要的原始组件回执重新计算，不能把岗位分布当成流程运行证据。

产品资料由 source 阶段先准备：`manual-acceptance-product-images.mjs` 按产品名称从 [固定款式素材](../../scripts/qa/fixtures/plush-products/README.md) 选取主图、侧面辅图和三张同款附图，通过正式附件接口补齐。两档的所有产品（含停用记录）逐图核对图位、文件类型与下载哈希；已有同款图复用，人工改图、文件冲突或名额不足时保留原资料。图片及提示固定随仓库保存，普通造数不依赖图片生成服务或外链。

生产准备由 `manual-acceptance-engineering-data.mjs` 沿用正式接口办理：为相关订单开放明细绑定本产品的有效 BOM，由工程确认资料、提交用料，再由老板和财务审核。工程确认读取对应产品图，不另外生成通用样品占位图；打印草稿与已确认快照仍按各自正式边界处理。

独立全验收按 `manual-acceptance-task-catalog.mjs` 准备九岗各 90 条状态样例，覆盖岗位实际允许的类型、风险、阻塞和处理结果。长期手测从同批销售订单和加工合同为八个可办理岗位各建 30 条带来源的跟进任务；老板岗位从同批真实审批任务取样。业务能力和已办理状态通过正式动作与逐条读回证明。

事实阶段除正常链外，保留三组生产草稿/取消、返工草稿/取消、库存预留/释放及出货草稿/取消。51 张出货单中仍只有一张 25 行长明细。生产异常保留 13 条来源驱动超领申请，另补 60 条独立在制批次申请：让步、报废、原厂返工、换厂返工、补料重做各 12 条，待审批、批准、退回和撤回各三条。质量处置由业务提出方案、质检提供判定，超领由生产提交，老板审批；批准样本保留待实际执行，撤回前未启动的审批不伪造流程锚点。

收款与付款分别覆盖草稿、待执行、退回、已过账、已冲销和已取消，每种至少三条；结算记录合计 40 条，另有客户预收、采购预付和委外预付各 18 条，以及对应退款各 18 条，合计 148 条；首款保留未用余额，退款核对原款、可退余额和冲销审计，不自动核销往来。红冲保留三条有效记录及三组原红冲 / 反向红冲，共九条，并核对每组来源、金额和关联。数量与状态通过正式动作产生，Workflow 结果和 Fact 入账分别读回。

事实造数的财务核对先分页读取本批单号与 ID，再通过正式详情接口实时读取状态、余额与快照；ID 索引只存于本次执行，不缓存业务状态。Readiness 使用绑定报告中的精确 ID 读取同一详情接口，逐项核对单号、来源、状态和字段，缺失或不符即失败。BOM 同样按版本 ID 读取，另核对产品 ID、版本标签和状态，不把 V1/V2/V3 当批次前缀；在制质检通过正式工序质检列表读取，采购及委外质检各走其来源接口。

工序回货仅从对应 WIP 批次办理；库存退回厂家使用独立的产品委外回货来源，两条来源分别核对，不能由工序合同补造库存回货。

附件提供可正常阅读的中文 PDF、图片、数量交期 XLSX 和近限制大小附件。整批造数还从同批产品图组为订单、规格、BOM、质检、草稿和已出货单据补对应的图片资料；加工合同的图样通过正式打印附页类型保存。

整批就绪核对的 `imageCoverage` 保存销售、生产、委外和出货的产品图引用，成品库存、质检样例，九岗位的任务图、状态分布和可搜索单号，以及业务附件读取结果。纯材料委外与无产品来源的独立任务保留正确的空图场景。浏览器缩略图、相册切换和导出 PDF 另做验收。

只读 readiness 完成后，在同一输出目录生成 `手测样本索引.md`，按当前菜单列出岗位、实际状态与单号。索引只投影同批实时读回，不另造数据；可办理记录被人工消费后保留结果，需要再次核对或使用新隔离批次，不回拨已过账状态。
日常从“测试数据 → 补齐手测数据”进入。确认本地环境后，统一场景脚本先通过 `scripts/seed-core-demo-data.sh --scenario-references` 核对或补齐单位与仓库，再执行共享业务阶段；无需先单独造基础资料。已有编号只有名称、类型或精度、启用状态均匹配时才复用；不符时停止并保留原记录。旧单位归并仍走正式 migration。Demo 与本地共用业务配方，Demo 的既有基础引用通过目标预检与 runner 校验。

来源资料阶段从客户、供应商和订单配方提取所需的公司共用付款方式。已有同名启用项直接复用；空库通过正式主数据接口新建并读回，停用或名称不匹配时先停止，保留目录原有设置。付款方式的准备结果记入来源资料回执。

开发工作台允许查询已持久化的旧 V5 / V6 回执，但新回执只能绑定当前批次，旧回执不能证明新版造数完成。

## 数据版本与历史回执

`dataVersion` 是后台校验冻结模拟数据基线的标识，日常造数无需选择或维护版本。纯样式、重构、性能优化及不改变数据结果的修复继续使用当前批次；每次开发反馈仍以新的 operation / batch、隔离库和 exact commit 留证。

只有单位含义、记录结构、生命周期 / 状态、业务链映射、稳定编码或数量合同发生不兼容变化，才集中升级 `dataVersion`。已持久落到本地或 demo 的冻结版本不得静默改写；旧基线保留用于说明当时测试内容。

`server/internal/manualacceptance/contract.json` 是这些版本值的唯一真源。`schemaVersion` 只表示合同结构，不随数据批次自动递增；`dataVersion / runId / visiblePrefix` 必须彼此一致。同一天可以冻结不同批次；合同不再登记配置修订或上一批次白名单，配置身份由受控 manifest 的完整内容推导。Go / JS 共同校验结构、模拟数据限制、单位 / 仓库与固定目标身份。

## 页面、业务链与证据合同

50 个正式验收目标统一登记在 `manual-acceptance-page-data-contract.mjs`。每页只能引用共享的 `role / source / task / facts / catalog` 阶段，不允许页面自带 builder、脚本或另一套 fixture；业务看板可以同时消费多个共享阶段，但不能另造页面数据。

`manual-acceptance-dataset-runner.mjs` 直接消费相同的阶段入口。新增页面、probe 或入口发生漏登、重复或分叉时，readiness 合同测试会 fail closed。

业务链回归统一从 `manual-acceptance-business-chain-contract.mjs` 读取观察台的同一份步骤目录：先选择业务链，再展开步骤绑定的责任、前置状态、动作、结果状态和 Fact，最后只把已登记的场景合同投影到现有阶段。

业务链、步骤和场景数量从 `DEV_FLOW_STATE_CATALOG.businessChains` 汇总，验收合同、核对计划和数据计划逐项校验相同的登记键与顺序，不另维护固定总数。每条链固定包含正常主路径、阻塞 / 退回 / 恢复、无权限、错误状态、取消 / 调整 / 冲正、重复提交 / 幂等六类。无权限和错误状态等非法结果只由合同测试或受控浏览器动作证明，不会为了覆盖而写入非法数据库状态。

图片、异常恢复和纠正的造数与验收标准见[完整模拟数据覆盖](../../.agents/skills/plush-seed-import-governance/references/full-dataset-coverage.md#coverage-contract)。样例索引使用同批可搜索的单据或任务号；结果按实际执行与读回记录，计划覆盖不计为已验证。

这个合同不新增 writer，顶层 `manual-acceptance-dataset.mjs` 和现有串行 runner 仍是唯一整批造数入口。

`/__dev/data-preparation` 的“覆盖内容”读取该合同的业务链、步骤与场景。点选链路只用于查阅。“测试执行 → 完整回归”（`/__dev/testing?view=full-acceptance`）使用现有 lifecycle 运行全部登记场景，成功或失败后自动清理临时库。

规范 apply 回执记录造数总 `startedAt / completedAt / durationMs`，并对 9 个阶段分别记录同样的真实耗时；未开始的阶段保持空值，不能冒充 `0 ms`。

计划和规范总回执同时保存 `chainDataDigest` 与 `chainVerificationDigest`。代码变化后按下表处理，不需要 Codex 定时同步平行清单：

| 摘要比较 | 旧数据结论 | 现在做什么 |
| --- | --- | --- |
| 两个摘要都相同 | 仍可用 | 保持当前 `dataVersion`，以新 operation / batch 绑定 exact commit 后继续回归 |
| 数据摘要相同，验证摘要变化或旧验证摘要缺失 | 只需重新核验 | 保持当前 `dataVersion` 和长期数据，以新 operation / batch 重跑合同、readiness 与受影响浏览器场景 |
| 数据摘要变化或旧数据摘要缺失 | 必须重新造数 | 先在新隔离批次修正；仅语义不兼容或冻结下一轮 UAT 基线时升级 `dataVersion`，不覆盖旧回执 |

上述三类判断适用于需要保留的同批数据；完整回归本身默认每次新建隔离批次，因此不会把旧数据库继续当作本次回归输入。旧回执仍保留用于比较对应旧计划和耗时，但不能证明最新代码已经回归。

模拟数据沿用永绅原文件的简短习惯，例如款号与品名分开、规格写成“米白·小号”、材料写成“米白短毛绒”、环节写成“裁片 / 车缝 / 电绣”，备注用“分两批交货”“颜色按样板”这类日常说法。来源资料采用当前批次编号（例如 `YS9-*`），岗位任务编号由所选 task profile 的合同生成；模拟身份还由 `datasetKey / dataVersion / runId` 和报告统一证明。原文件只用于理解字段和用词，不直接导入真实行。

本地日常手测统一使用现有开发入口和登记开发库 `plush_erp` 中的一份 `scenario-demo` 数据。场景有变化时复用或局部刷新这份数据；批次标识用于幂等和读回核对，不对应另一套常驻入口或数据库。本地 fresh 隔离库只用于一次性验收，由 lifecycle 在验证结束后清理。

可重建的本地模拟业务数据不做备份；经明确授权可在原库清空业务数据后按同一配方重建。清空先 dry-run 核对目标和业务表范围；账号、配置及其他环境的恢复点按各自合同管理。

本地 `scenario-demo` 和 `demo-133` 的常规准备按稳定编号写入或读回，保留无关历史。只有明确选择 fresh 隔离库或另行授权的数据库重建时，才应用下表的空业务基线；远端 fresh generation 还必须绑定重建回执与实时零业务数核对。

| --- | --- | --- |

## 整批执行顺序

正常整批写入只使用顶层 runner。它按 `core → baseline → role → source → task → facts → purchase-quality → attachments → readiness` 串行执行；两端 handler 身份和 target-free 业务输入相同，目标适配层只提供 endpoint、数据库身份、凭据、确认、带外证明和报告目录。

`core` 在登录前先调用只读 `/readyz/runtime-identity`，用摘要同时绑定实际数据库、完整 40 位 release commit 和 14 位 Atlas revision；探针只返回匹配 marker，不返回数据库名或连接信息。

随后登录 admin 读取真实 `debug.capabilities`，再次核对数据库、运行环境和六个 debug=false，只读证明后续阶段依赖的 8 个稳定单位和 4 个仓库。`baseline` 再逐类读回客户、供应商、材料、产品、SKU、工序、BOM、来源单、Workflow 和全部 Fact 都为 0；任何已有业务记录都会阻断，不能用历史数据凑页面数量。

`role` 在已注册的 local 与 133 验收目标中读取岗位当前完整设置，再统一通过带版本校验和审计的 `admin.set_role_settings` 整包回写原权限、原菜单布局和新的仓库范围，把 `warehouse / quality` 精确绑定到这 4 个核心仓库；不得分拆写入、丢失导航顺序或用脚本直写 RBAC 表。

材料、产品、工序、BOM 与业务源单数量随后由 `source` 阶段独立写入并读回。密码创建与重置统一要求 8～20 位且 UTF-8 编码后不超过 72 字节；本地从环境变量读取，133 从固定测试凭据合同读取，报告均不保存密码。

生产事实配方由 `manual-acceptance-source-data.mjs` 的 `MANUAL_ACCEPTANCE_PRODUCTION_RECIPE` 同源声明，source、fact 和顶层 semantic plan 共同消费。

45 套生产均走正式 `PLUSH_SEW_HAND_V1` 的裁片、车缝、手工、包装路线；每套明确选择一个 BOM 材料需求与唯一已确认委外行，其余材料按冻结需求正式领用。45 条专用委外行分配在既有来源合同内，不增加 acceptance 的 45 张或 volume 的 450 张来源委外单；混合销售来源的合同清空单一来源单号，实际关联保留在生产明细、BOM 需求与 WIP 委外分配。

配方包含客户验货与包装版本快照，并保留返工和异常处理。缺少路线、来源粒度漂移或旧配方报告均拒绝；既有 stage 指纹与业务 semantic 身份共同阻止旧批次续跑，不以直接完工或 Workflow 完成代替正式事实入账。

收付款及核销结束后，事实阶段按本批单号和 ID 重新读取应收、应付等财务记录，再生成状态分布与字段摘要。就绪检查逐项对账，不沿用收付款前的状态快照。

正式 browser 各登记模式按顶层报告明确的 `sourceScaleProfile` 重建当前 target plan，核对当前 semantic 与 stage 指纹，旧配方报告不能直接接入验收；shared opt-in 仍固定 volume 与长期基线。readiness 同时提供 source 和 facts 时校验两者的来源 semantic 同源，不把它们等同顶层 digest；独立组件检查没有顶层 bundle 时，不宣称已证明当前整批配方。

## 本地隔离验收与自动清理

`local-acceptance-lifecycle.mjs` 是本地完整验收的统一入口：它只接受登记的 `192.168.0.133:5432` 开发 PostgreSQL、clean exact commit、按批生成的 `plush_erp_acceptance_<run-id>_dev` 与 `plush_erp_acceptance_<run-id>_browser_actions_dev`，并使用隔离端口完成建库、migration、后端、十个单岗位模拟账号与一个财务兼采购账号的受控预配置 bootstrap、客户配置、core、九岗位数据、50 项只读浏览器和三条真实写异常流。

预配置 bootstrap 只在 runtime identity、精确数据库、环境、super admin、目标确认和账号确认均通过后走 `admin.create`，不直写账号表；它先满足客户配置审批责任岗位的“有可办理员工”发布门禁，dataset role 阶段仍会重新核对账号并补齐正式岗位权限和仓库范围。

浏览器启动前会重新扫描规范辅助端口，并在健康检查后复核本轮 Vite 子进程仍存活，不能把并发任务占用端口上的外部页面误认成本轮服务。只读验收完成并停后端后才克隆 `browser_actions` 库；无论成功失败都会停服务、逐库强制删除和读回残留，清理失败返回非零并报告精确库名。

收到 SIGINT 或 SIGTERM 时，当前步骤返回后停止进入下一步。验收入口先停止自己启动的服务与子进程，再清理隔离库并写入中断回执。

默认只打印 plan；真实执行必须传入 exact commit、run id、由 plan 生成的确认串和 `LOCAL_ACCEPTANCE_DATABASE_BASE_URL`，回执不保存 DSN、密码或 token：

```bash
node scripts/qa/local-acceptance-lifecycle.mjs \
  --commit '<clean-40-character-commit>' \
  --run-id 20260728-delivery

LOCAL_ACCEPTANCE_DATABASE_BASE_URL='postgres://<user>:<password>@192.168.0.133:5432/postgres?sslmode=disable' \
  node scripts/qa/local-acceptance-lifecycle.mjs \
    --execute \
    --commit '<clean-40-character-commit>' \
    --run-id 20260728-delivery \
    --confirm 'RUN_LOCAL_ACCEPTANCE_LIFECYCLE:plush_erp_acceptance_20260728_delivery_dev:plush_erp_acceptance_20260728_delivery_browser_actions_dev:<clean-40-character-commit>'
```

### 造数执行快照

本地开发与 Demo 共用 `scenario-demo-data.mjs` 和九阶段 runner。每次 apply 在任何业务写入前保存代码与参数，失败也保留执行回执；不要求工作区干净，不自动 commit、push、部署或迁移。服务器实际 SHA 与本地 Git 基准 SHA 分别记录，服务器 SHA 必须在本地 Git 对象库中可核对，且当前后端 / 数据库源码与该提交一致。未提交的造数脚本与前端修改可使用；未部署的后端修改须先发布后再造数。

| 记录 | 保存方式 |
| --- | --- |
| 执行时间与批次 | `receipt.json` 保存 UTC 毫秒时间、状态及“时间戳 + 短内容指纹”；页面按用户时区展示。业务基线 `dataVersion` / `runId` 保持原幂等含义 |
| 代码 | `output/qa/scenario-generations/code/<完整指纹>/source.tar.gz` 与 `manifest.json`；读取 Git 登记和未忽略的新源码的当前字节，包含未提交修改和删除结果，按路径、内容和执行权限计算 SHA-256；相同内容仅存一份 |
| 参数 | `output/qa/scenario-generations/runs/<执行 UUID>/parameters.json`；冻结规模档、完整业务计划、目标、迁移、配置身份、本地基准提交 / dirty / 工作区指纹和 Node 版本 |
| 结果 | 同目录 `receipt.json`；成功后另存 `result.json`，包含业务读回、实际任务时间安排和阶段复用信息。业务调用失败或执行期间源码改变记为 `not_proven`，不能自动重试 |

源码快照仅包含 `scripts / server / config / web / deployments` 中的公开源码及根依赖清单；排除测试、文档、构建输出、依赖目录、`.env*`、`*.local.*`、凭据 / 密钥文件与符号链接。代码范围比阶段逻辑指纹更广，用于追溯整次执行；页面或非造数代码修改可能改变快照指纹，但仍由原阶段逻辑指纹决定是否局部刷新，不据此全量重造。目录仅当前用户可访问，文件仅当前用户可读写；参数采用固定字段，不保存进程环境、密码、token、DSN 或原始命令。

工作台自动用 operation UUID 关联快照；CLI 也自动生成 UUID，可用 `--execution-id <UUID>` 显式关联。快照编号可在“排查信息”复制。重复使用同一 UUID 不覆盖历史。只读计划不落快照；开始、失败或未知结果不表示成功造数。执行前后核对源码与计划，读取回执及复用存档时验证参数、清单和压缩包指纹，损坏时拒绝继续。业务调用返回后若结果或快照无法核验，操作记为 `not_proven`；损坏的快照在记录页明确提示“校验未通过”，不妨碍查看其他记录。

需要查阅原代码时，在仓库根目录将对应存档解压到一次性独立目录；不要覆盖工作区。存档不包含运行凭据、依赖安装目录或数据库备份，`result.json` 的复用记录也不等于原数据库状态。重新执行仍需恢复适当工具链、取得当前凭据，核对目标版本 / 迁移 / 既有数据并重新生成计划和确认；不能直接重放旧确认串。

每个阶段回执同时记录由登记入口、阶段实现及显式依赖文件计算出的逻辑指纹。逻辑指纹未变时，数据写阶段直接复用原组件回执；某阶段指纹变化时，只重跑该阶段及依赖它的后续阶段。仅 release SHA 变化不会重造业务数据，core 和只读 readiness 仍会实时重验；migration 变化会刷新 baseline 及全部后续阶段。

当前执行回执合同 `manual-acceptance-dataset-runner-v10` 只标识已保存回执的读写约定，不表示模块的代码版本。该合同下缺少阶段指纹的回执无法证明数据来自当前逻辑，因此首次 resume 必须一次性刷新完整阶段链并写入指纹；后续才按变化阶段与依赖闭包增量刷新。指纹伪造、依赖未登记或目标范围漂移仍失败关闭。常规部署不得因为“发布过一次”无条件重跑九阶段造数。

fresh apply 会在开始时捕获一次岗位任务时间锚点并写入总回执；同批 resume 必须校验并复用该锚点，不能按当前时间重排到期日。业务数据版本中的日期只用于来源单业务日期，不再充当任务到期锚点。本地和 133 共享同一时间策略与语义 digest，但分别在自己的 fresh 回执中绑定执行锚点。浏览器必须在回执记录的有效期内同时看到出货放行的“即将到期”和“已超时”；锚点过期后不得继续沿用旧报告宣称通过，应换新数据版本并从 fresh 空库重放。

`readiness` 独立命令保持严格非绿：41 项可查询数据全部通过、5 项模板预览与 5 项打印工作台仍待浏览器时，报告为 `queryChecksPassed=true / queryEvidenceComplete=false` 并退出 1。

顶层 dataset runner 只在“0 项查询失败、恰好这 10 项打印目标 `not_proven`、其余 41 项全过”时把数据底座记为已证明，同时明确写入 `browserEvidencePending=true`；任意其他缺口仍立即阻断。浏览器还必须为 5 个预览各证明至少 1 份可见数据，并为每个打印工作台证明本批来源至少 5 条，再打开精确 25 行单据和真实 PDF。

最终只有同批浏览器报告的 `acceptancePassed=true` 才能宣称 50 项自动化验收完成。

出货数据是精确合同：同批必须恰好 47 张出货单，且恰好 1 张有 25 行明细。fact 写入报告、readiness 读回和出货页面 DOM 任一出现 45、46、48 张，或出现零张/多张 25 行单据，都必须失败。

附件入口绑定同批源单、事实和任务报告，按岗位权限上传并做列表与下载读回。133 还必须提供 `MANUAL_ACCEPTANCE_TARGET_CONFIRM` 和 `MANUAL_ACCEPTANCE_TARGET_ATTESTATION_JSON`，证明精确 target、origin、customer、release、migration 及全部 debug=false；未绑定最终 commit / image 时不得写 133。

最后执行真实浏览器只读核对。页面能打开、页面有数据、数量达到门槛和人工确认是四类不同证据，不能合并成一句“已验收”：

列表先通过正式 UI 选择“全部记录 / 不限状态”并清除单据精筛，再记录明确分页或状态范围的总数、计量单位和查询范围。

源数据按对应正式 probe 的完整本批查询前缀过滤，所有实际渲染行均须属于该前缀，过滤总数须与同单位、同查询范围的绑定来源一致；采购单和加工合同的页面广搜索还会命中关联材料或来源单据，而 readiness 按单号后置收窄，因此这两页改按 source steps 的完整 ID / 单号集合逐页采证，广搜索总数不能当本批数量。

该集合必须与当前规模纯计划的全部源单号精确闭合；只含已审批或已确认单据的 referenceRecords 不能替代整批。数量范围独立于随后代表单据的类别前缀，例如 BOM 数量包含来源 BOM 和工程 BOM，不能用较窄的来源类别总数替代。

事实、正式账号与业务协同任务按 canonical 单据 ID / 完整业务号 / 任务码逐页核对到原最低数量，历史或额外记录不计入本批；协同任务从编号列的独立完整值和真实任务 ID 核对，不能把来源单据 ID 或编号与任务名拼接的文本当任务编号。

随后另行定位代表单据检查字段与详情，并分别保留 `quantityScope`、`currentBatchProof` 和最终筛选范围；一条精确搜索结果不能证明全批 45 条，产品数量与 SKU 数量、库存批次与余额数量不得互换。

## 共享开发库的只读验收

登记共享开发库的长期 `scenario-demo` 批次使用同一 50 项浏览器目录，必须显式加 `--scenario-demo-shared-local`（API 为 `scenarioDemoSharedLocal: true`）。

该模式只接受既有 target policy 登记的长期开发库、后端 `http://127.0.0.1:8300` 和当前版本 `scenario-demo/` 下原位 canonical 报告，要求 `volume` 配方、全部完成阶段、component digest、当前阶段逻辑指纹及正式 persistent baseline。

它证明长期保留批次的精确创建或读回，不把该基线表述为 fresh 或隔离空库；不得复制、改名报告或使用 lifecycle/local alias 替代。

共享模式在业务与打印读取前及结束时，分别绑定 clean Git SHA、当前完整源码指纹、正式 active bundle 的后端源码指纹、`runtimeServerVersion(bundle)` 和数据库 / migration 运行证明；正常正式账号登录后通过已有 `get_effective_session` 只读核对当前登记客户配置，不要求增加 debug 权限或管理员凭据。

Git SHA 与 `local-*` 运行版本分别记录，不将本地运行版本当作裸 SHA。账号登录与知悉确认仍会写认证或行政记录，业务数据只读；物理重建与 OID 恢复证明仍由独立受控操作留证，不成为浏览器的自造回执依赖。默认 local 隔离验收及 `customer-trial-133` 的目标、账号、空基线和 attestation 合同不变。

```bash
scenario_reports=output/qa/manual-acceptance/datasets/2026.11.07-v9/scenario-demo
MANUAL_ACCEPTANCE_PASSWORD='<local-demo-password>' \
```

本地 Kratos BBR 若在逐页读取期间返回纯 HTTP 429，浏览器验收会按 10 / 20 / 30 秒递增等待，最多执行四次，并在报告保留每次失败事件与截图。只要混入其他运行时错误、最终页面数据不足，或第四次仍被限流，整轮验收仍失败；该重试不能把持续过载或业务错误改写成绿色。

## 隔离库异常流程写入验收

三条异常流真实写浏览器验收必须单独使用名称和归属明确、可回收的全新本地隔离库。

数据库名必须由 `database-target.mjs` 的 `browser-actions` 生命周期生成并匹配 `plush_erp_acceptance_<run-id>_browser_actions_dev`，后端必须是 loopback 且不能使用共享端口 `8300`，显式确认串必须同时绑定数据库名与后端 origin；runner 启动后还会用 `/readyz/runtime-identity` 复核同一数据库身份。

禁止指向日常共享开发库、133 上其他实例、客户试用或生产数据库。

三条流程使用独立业务来源；单条失败会保留诊断并继续核对其余流程，最终必须三条全部通过且失败列表为空。运行身份预检失败仍立即停止，不执行业务动作。

页面导航、故障路由撤销和会话关闭前复用真实 RPC 完成等待，避免未结束的转发回调使进程退出而跳过清理。后台转发失败以脱敏的路径、方法和 `status: 0` 归入验收失败，仍走报告与清理；不输出 Playwright 原始请求头。

```bash
MANUAL_ACCEPTANCE_DEMO_PASSWORD='<local-demo-password>' \
EXCEPTION_FLOW_BROWSER_CONFIRM='RUN_ISOLATED_EXCEPTION_FLOW_BROWSER_ACTIONS:plush_erp_acceptance_exception_example_browser_actions_dev:http://127.0.0.1:8323' \
  node scripts/qa/exception-flow-real-write-browser.mjs \
    --base-url http://127.0.0.1:15214 \

    --database-name plush_erp_acceptance_exception_example_browser_actions_dev \

```

该 companion 登录后先停在轻量工作入口，等待账号、客户配置和知悉状态稳定，再开始业务读回；任一页面响应出现 HTTP 4xx / 5xx 都会保留脱敏路径和方法并使验收失败。主业务 mutation 由真实产品 UI 点击触发；直接浏览器上下文 RPC 只用于结构合法的无权角色负例、权威读回和重复 / 旧 version 重试。

未知结果场景是在后端已经返回成功后丢弃浏览器响应，再由页面权威读回确认，不 mock 业务成功。报告会明确记录 `admin_users.last_login_at` 的 `auth-write`、三条业务写、三个服务端 `40304`、三个 simulated transport fault、终态 Fact / 库存 / 核销读回及 `40920` CAS 拒绝。

Finance Payment 使用隔离数据集中已经批准的来源，Inventory Adjustment 由浏览器新建并办理老板审批与仓库执行任务，Production OVER_ISSUE 使用已批准额度并由真实领料 Fact 消费后取消恢复。它不证明其他岗位、IQC / 委外写动作、打印工作台、部署、客户账号或客户 UAT；这些证据继续按各自验收层级单列。
