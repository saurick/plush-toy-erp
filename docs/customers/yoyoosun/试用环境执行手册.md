# 永绅 yoyoosun 演示造数执行手册 / Yoyoosun Demo Data Runbook

本手册用于在本地隔离验收库和 `demo-133` 重放同一版脱敏模拟数据，支持项目演示、培训、流程验证和回归。它不适用于甲方测试环境 `customer-test-133`，也不代表任何真实客户业务事实或签收。

## 1. 固定合同

数据集身份由 [`contract.json`](../../../server/internal/manualacceptance/contract.json) 统一登记。执行时使用生命周期计划输出的当前值，不能从历史回执或文档中的旧批次复制参数。

### 数据与本地验收

| 项目 | 固定值 |
| --- | --- |
| 数据集 | `yoyoosun-manual-acceptance` |
| 数据合同版本 | 合同中的 `dataVersion` |
| 运行批次 | 合同中的 `runId` |
| 页面验收目标 | 50 项：2 个登录与入口、29 个电脑业务页、9 个岗位任务页、5 个打印预览和 5 个打印工作台 |
| 来源单可见前缀 | 合同中的 `visiblePrefix` |
| 岗位任务前缀 | 由当前数据合同和任务计划生成，以对应批次回执为准 |
| 本地验收库 | 每批 `plush_erp_acceptance_<run-id>_dev`；真实写 companion 为同批 `*_browser_actions_dev` |
| 本地岗位账号 | 十个单岗位 `demo_*` 与一个财务兼采购账号；密码只从本机受控环境读取 |

### 演示目标

| 项目 | 固定值 |
| --- | --- |
| 部署 target | `demo-133` |
| 内部数据 target | `customer-trial-133`，只用于模拟数据合同，不是部署环境 |
| demo 数据库 | `plush_erp_demo_v1` |
| demo Compose project | `plush-toy-erp-demo-v1` |
| demo 端口 | PostgreSQL `55436` / 后端 `8325` / 前端 `5195` |
| demo 根目录 | `/root/deploy/plush-toy-erp-demo-v1` |
| demo 公网入口 | `https://demo.yoyoosun.net` |

这些数据是 seed / fixture / 模拟业务事实，不得描述为真实客户、库存、出货、财务或验收结果。两端使用同一业务语义和数量合同，但数据库 ID 各自生成；禁止复制数据库行或把“编号相同”写成“两端内容身份相同”。

`test.yoyoosun.net` 是甲方测试/验收环境，必须使用独立数据库、上传、Compose project、端口、env、备份、rollback point、operation 与 smoke。普通部署保留甲方已录入的数据；只有开始新一轮测试且显式执行独立 rebuild operation 时才恢复干净基线。demo 造数绝不能进入 test。

正式环境 `erp.yoyoosun.net` 对应独立的 `production-133` target，不参与本手册的造数与重建；退役的 `admin.yoyoosun.net` 不参与任何 target、清理、健康检查、发布或回滚动作。

## 2. 安全边界

- 造数只走正式 JSON-RPC / usecase；不复制表行，不运行临时 SQL，不把 Workflow payload 冒充 Fact。
- 不因模拟数据放宽权限、状态、幂等、客户配置、数据库身份或生命周期门禁。
- 本地只使用隔离端口和一次性数据库；成功或失败都停止服务、删除本批数据库并读回零残留。
- demo 只能命中 `plush_erp_demo_v1`。任何数据库、host、port、release、migration 或 PostgreSQL generation 漂移都停止。
- demo 重建前必须有 fresh backup、隔离恢复验证和精确 rollback point；旧物理数据代与 dump 不自动删除。
- `customer-test-133`、`production-133`、共享开发库、客户真实资料和其他项目数据库均不在本手册的造数写入范围。
- steady runtime env 不保存 bootstrap 密码；凭据、token、DSN 和客户正文不进入日志或 evidence。
- 写入门禁必须证明“fresh 空库基线已记录”；未取得当前回执时停止，不把历史空库结论复用于新候选。
- 客户配置用 `customer-config-effective-session-probe.mjs` 读回；未登录探针必须保持 `40302 未登录`，不得为造数放宽认证。
- 模拟数据不等于真实 import；本地或 demo 技术回执不证明目标环境发布、真实客户导入、客户签收、备份恢复或 release evidence 已完成。

## 3. 本地完整技术验收

优先使用统一生命周期入口。默认命令只生成计划，不连接数据库；真实执行必须使用该计划给出的 exact confirmation：

```bash
node scripts/qa/local-acceptance-lifecycle.mjs \
  --commit '<clean-40-character-commit>' \
  --run-id '<unique-run-id>'
```

生命周期创建同批只读验收库和 `browser_actions` 真实写 companion，完成 migration、岗位模拟数据准备、50 项页面/PDF 读回及登记真实写流程；无论成功失败都停服、删库并证明零残留。该回执只证明本地 exact commit，不证明 demo 已部署。

## 4. demo 部署与重建前置

开始远端造数前必须逐层证明：

1. exact SHA 已通过 canonical GitLab `CI Gate`。
2. v2 七资产不可变 Release 与同一 release rehearsal 完整。
3. `demo-133` 已 promotion 到该 release，Compose、image/content identity、migration、health、ready 与公网 SHA 一致。
4. 当前目标没有未结束的 promotion、rollback 或 database rebuild operation。
5. 需要重建时，controller 的 plan 为 `eligible`、operation 为 `ready`，即时 target preflight 按正式资格合同通过，backup 已恢复验证，旧物理数据代与 rollback identity 已绑定。

受控重建：

```bash
node scripts/deploy/database-rebuild-controller.mjs \
  --release-manifest '<exact-release-manifest.json>' \
  --target demo-133 \
  --idempotency-key 'rebuild-database:demo-133:<release>:<change-id>' \
  --json

node scripts/deploy/database-rebuild-executor.mjs \
  --operation-id '<ready-operation-uuid>' \
  --release-manifest '<same-exact-release-manifest.json>' \
  --confirmation 'REBUILD_DATABASE:demo-133:<40-character-release>:<ready-operation-uuid>' \
  --json
```

`failed` 只表示旧运行态已被证明恢复；`not_proven` 必须先只读核对数据目录、容器、migration、release 与 rollback point，禁止重试。`passed` 只证明 fresh 物理库、首个管理员、空业务基线和基础运行态；不等于模拟数据、页面或客户验收已完成。

数据库重建回执中的恢复检查只覆盖 PostgreSQL，不自动切换附件 bucket 或建立新的附件物理代，也不能证明附件已恢复。需要成套恢复保证时，按[备份恢复手册](../../../deployments/yoyoosun/runbooks/04-backup-restore.md)绑定同一 PG dump 与全部登记附件，完成独立隔离 PG/S3 恢复、对象校验和临时资源清理，保留单独回执。

fresh 库尚无 active config 时，正式重建资格只允许延后明确读回为 `customerConfigState=absent` 的 `target_customer_config_readback_failed`；它仍是 blocked preflight，不能记为完整通过。其他 blocker、配置 invalid/unknown 或未证明为空的读取失败均停止；后置配置和造数完成后须重新取得完整 passed preflight。

本轮环境登记不要求立即重建 demo，也绝不授权清理 test。

## 5. migration 与管理员初始化

所有 target 路径、project、数据库、端口和锁以 `scripts/deploy/deployment-targets.json` 为真源。demo migration 只通过：

```bash
DEPLOYMENT_TARGET_KEY=demo-133 \
  sh server/deploy/compose/prod/migrate_online.sh --status-only

DEPLOYMENT_TARGET_KEY=demo-133 \
  sh server/deploy/compose/prod/migrate_online.sh
```

本节说明分段初始化入口，写入仍须既有 prepare / confirmation / maintenance 门禁。

fresh 数据库完成 migration 后、常驻 `app-server` 启动前，使用 `bootstrap-production-admin.sh --deployment-target demo-133` 的受控入口；成功后立即回到 `BOOTSTRAP_ADMIN_ONCE=false` 且不含 `APP_ADMIN_PASSWORD` 的 steady env。

正式 rebuild 为 passed 时已完成 migration 和首个管理员，不重复执行这两步。

## 6. 激活 demo 客户配置

fresh 库先使用 `manual-acceptance-account-scenarios.mjs --apply --formal-accounts-only` 准备十个单岗位 UAT 与一个财务兼采购账号，显式绑定当前 target、backend URL、database、data version 和 run id。

该入口使用首个管理员的临时凭据、exact target confirmation、`MANUAL_ACCEPTANCE_FORMAL_ACCOUNT_CONFIRM` 与 target attestation；它先满足配置审批责任岗位的员工前置，完整 dataset 的 role 阶段仍会核对权限和仓库范围。

参数与确认串见[正式账号入口](../../../scripts/qa/manual-acceptance-account-scenarios.mjs)。

随后完成当前配置包的 `validate -> publish -> transition check -> activate -> effective-session readback`。

客户配置组件从受控环境读取临时管理员凭据，并要求 `MANUAL_ACCEPTANCE_PASSWORD` 用于独立性校验；目标 UAT 凭据仍按 `MANUAL_ACCEPTANCE_UAT_PASSWORD` 和凭据合同读取。demo 使用部署 target `demo-133`，数据入口仍传内部 `customer-trial-133`：

```bash
node scripts/qa/customer-config-runtime-manifest.mjs \
  --customer yoyoosun \
  --mode preview \
  --out output/qa/manual-acceptance-dataset/yoyoosun-runtime-manifest-preview.json
```

应用配置时必须同时绑定：

- `target=customer-trial-133`
- `databaseName=plush_erp_demo_v1`
- 当前 release、migration、data version 与 run id
- `ERP_ALLOW_CUSTOMER_TRIAL_CONFIG=1`
- `ERP_CUSTOMER_TRIAL_TARGET=customer-trial-133`

这些开关只允许 demo 使用。customer-test 与 production 必须保持关闭。

## 7. 基础资料与模拟业务数据

配置激活后，先运行镜像内一次性 `bootstrap-manual-acceptance-core` 并正式读回；core 只创建或复用当前合同的单位和仓库，发现身份漂移时整批失败，不创建客户、订单、Workflow 或 Fact。fresh 首轮随后按下一节运行官方凭据轮换，将 admin 和完整 11 个 UAT 账号切至 demo 凭据合同，再执行完整 dataset runner。

fresh apply 前须校验 canonical rebuild receipt 的 operation/plan/hash 来源及当前物理 generation。

通过后，将 `output/qa/manual-acceptance/datasets/<data-version>/customer-trial-133/` 的旧目标目录完整归档，保留全部文件 hash 和恢复点，再建立新 canonical 槽位。存在 `dataset/.apply.lock` 或现场归属不明时停止检查；不得删除单个报告或锁来制造 fresh 资格。

dataset 自己仍会重新核对允许的空业务基线。

dataset runner 在写入前必须读回：

- exact release、migration、数据库与 PostgreSQL generation；
- active customer config revision / source；
- fresh baseline 或允许增量的长期 Scenario 身份；
- 当前 operation 与幂等批次；
- 受管业务对象计数。

完整模拟数据继续使用内部 target：

```bash
node scripts/qa/manual-acceptance-dataset.mjs \
  --apply \
  --target customer-trial-133 \
  --source-scale-profile volume \
  --data-version '<current-data-version>' \
  --run-id '<current-run-id>' \
  --confirm '<exact-confirmation-from-current-plan>' \
  --target-attestation-json '<current-release-and-migration-attestation-json>' \
  --database-rebuild-receipt '<current-passed-rebuild-receipt>'
```

先以 `--source-scale-profile volume --data-version '<current-data-version>' --run-id '<current-run-id>'` 输出当前 JSON 计划，从中读取版本、批次和确认串；计划模式不接受 target 或 apply 绑定参数，顶层 CLI 也没有 `--json` 开关。

实际执行时，顶层 dataset 与 browser CLI 必须显式通过 `--target-attestation-json` 绑定 exact release、migration、数据库和全部 debug=false，它们不读取同名环境变量。账号与客户配置组件可从 `MANUAL_ACCEPTANCE_TARGET_ATTESTATION_JSON` 读取相同声明。

该 JSON 只含脱敏目标身份；远端不接受 `--database-name`、`--expected-release` 或 `--expected-migration` 来代替 attestation。登录输入只从受控进程环境读取，不写入命令历史、报告或仓库。

演示使用 `volume` 来源规模，与本地长期演示默认档一致；完整隔离验收继续默认轻量 `acceptance`。两档的当前数量见 [QA 数据规模合同](../../../scripts/qa/README.md#全页面试用验收数据)，规模选择必须贯穿计划、执行和回执。大规模来源数据仍运行相同岗位、事实和异常链，不代表所有来源单都已过账。fresh apply 前保留原批次报告与重建恢复点，不覆盖旧回执。

工序扩容保留裁片、车缝、手工和包装四个生产节点的唯一工序绑定；其余模拟工序作为普通工序使用。数量扩大不增加生产节点的绑定数量。

事实阶段另准备 3 条独立未入库到货草稿，分别形成待复检、复检合格和复检不合格样例；原检验判定、检查项及纠正原因保留，新复检通过正式接口与原记录关联。读回至少 57 条到货单和 63 条来料检验记录，重复执行须复用同一复检记录。新增样例不进入采购拒收处置、库存或财务过账；记录纠正复检不等于完成任务或新增库存事实。

## 8. 凭据与 smoke

demo 测试账号合同以 `deployments/yoyoosun/env/credential.contract.json` 为真源。fresh 首轮按“formal 账号 → config → core → 凭据轮换 → 完整 dataset”执行；恢复或回滚后需要轮换时，仍独立核对当时身份与恢复点。轮换与最终 smoke 分别留证：

1. 运行 `deployments/yoyoosun/scripts/rotate-credentials-133.sh`，绑定 exact release、migration 和 operation id；闭包会在目标锁内先创建 operation-bound 备份，完成隔离恢复校验并清理恢复库，再原子发布备份和轮换凭据。调用方不得传入备份路径、hash 或其他备份身份。
2. 未知输出只在 exact 备份与服务端 durable marker 已成对存在时使用相同 operation id 读回；若中断只留下备份而没有 marker，保留半状态证据并用新 UUID 重新准备当前 live state 的受控备份，禁止删除旧备份或把它冒充新 rollback point。marker 存在但 exact 备份缺失时停止处理。脱敏回执中的 rollback point 必须与服务端持久化 operation 一致。
3. 完整 dataset 和浏览器检查结束后，运行 `scripts/deploy/run-smoke.sh`，验证完整账号矩阵、health、ready、customer config effective session、PDF 与公网 exact SHA。只运行账号与 SMS capabilities 子集时，只能声明该子集通过；`auth.capabilities` 不发送短信，也不证明真实短信收发。

脚本只通过 stdin 向当前远端进程传递受控输入，报告不保存密码、token、手机号、HTML、PDF 正文或 raw response。

## 9. 浏览器验收

浏览器必须实际连接 demo 公网入口并核对：

- 2 个登录与入口目标及客户配置身份；
- 29 个电脑业务页和 9 个岗位任务页；
- 5 个打印预览和 5 个打印工作台；
- 受管对象数量、状态、来源单和 Workflow / Fact 边界；
- `system.version` 的 exact SHA / release；
- 目标 operation、备份与 rollback point。

上述页面范围以[canonical browser catalog](../../../scripts/qa/manual-acceptance-catalog.mjs) 的当前 50 项目标为准。浏览器不执行业务写入，但登录与法律提示确认会留下数据库记录，不能描述为数据库完全只读。本地截图、历史回执或单一健康页不能替代当前浏览器读回。测试结果不得表述为甲方签收。

## 10. 完成定义

只有以下证据全部绑定同一候选 SHA/digest，才能说“demo 模拟数据环境已完成”：

1. target registry、Compose、端口、数据库、上传、备份与 rollback identity 独立；
2. migration、管理员、客户配置和数据批次读回一致；
3. health、ready、system.version、完整账号矩阵、PDF 与 50 项浏览器验收绿色；
4. 公网 DNS/TLS/入口指向 demo，自身 operation 终态可读；
5. customer-test 未被写入或污染。

该结论不等于 `customer-test-133` 已恢复干净基线，也不证明 `production-133` 的发布或验收状态。
