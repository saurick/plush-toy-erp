# 变更请求流程 / Change Request Process

本流程只处理明确归属 `yoyoosun` 的客户输入及其后续变化。它不承接普通产品 / 研发输入，不创建 Change 模块，不新增 `change_records`、每会话文档或第二套需求台账。

## 来源与客户范围

| Codex 会话输入 | 归类 |
| --- | --- |
| 未明确标注甲方提出 / 要求 / 反馈 / 确认 | 项目负责人借助 AI 形成的产品 / 研发输入，不写入 yoyoosun 需求来源 |
| 只写“甲方” | 当前阶段指唯一客户 `yoyoosun` |
| 明确客户名称或 customer key | 只归该客户；不是 `yoyoosun` 时不写入本目录 |
| 写“甲方已确认” | 先归到明确客户，再由 Private 仓库会议纪要、签字版、邮件或等价受控来源证明确认 |

以后出现多个客户时，不从旧会话或其他任务沿用客户身份；当前会话无法确定且会显著改变结果时才询问一次，不猜测客户。

## 记录路由

1. **甲方初始输入**：明确客户来源、业务场景和样本进入[需求线索](需求线索.md)。
2. **产品 / 研发最小闭环**：当前行为只在正式产品 / 架构文档、代码、schema、migration 和测试中维护一份；普通正确性和易用性不逐项建需求或决策记录，只有影响长期产品合同或用户行为的选择进入[决策日志](决策日志.md)。
3. **甲方后续修改**：只有再次明确标注客户来源才按该客户变更处理；已确认或已实施行为的变化按下节追加决策，不改写初始输入或旧决定。
4. **未决项**：尚未决定的客户业务选择进入[问题待办](问题待办.md)，产品 / 研发推断进入[假设登记](假设登记.md)。

线索与决策只解释来源和变化原因，不复制完整实现规格。

## 后续修改

1. 尚未确认或尚未实施的澄清，更新原问题或假设，不制造一条“变更历史”。
2. 已确认或已实施的业务行为发生变化时，新增决策并写清替代关系、适用客户、生效范围和历史处理；不覆盖旧决定。
3. 只改变未来行为时明确仅新单 / 新版本生效；影响已生效订单、库存、生产、出货、财务或审计时，必须评审版本化、迁移、调整或冲正。
4. 按钮位置、业务化文案、清晰反馈、来源明确的自动带值等普通易用性优化不登记为客户业务变更。

## 步骤

1. 按[模块实施治理](../../product/模块实施治理.md)核对输入类型、客户范围、当前真源、最小闭环、待确认项和历史影响。
2. 判断采用 Product Core、Industry Template、Customer Config、Customer Extension、Data Import Adapter、Print Template Candidate、Reporting 或 Deferred。
3. 涉及库存、出货、质检、财务事实时，必须进入架构评审。
4. 只服务 yoyoosun 的内容先进入 `docs/customers/yoyoosun` 或 `config/customers/yoyoosun`。
5. 可以通用化的内容再进入 `docs/product/*`、`docs/architecture/*`、schema、usecase 和 tests。
6. 每轮实现必须说明输入来源与客户范围、产品 / 研发补齐内容、记录去向、验收命令、历史影响和剩余风险。

## 禁止

- 不把“甲方提过”直接等同 Product Core。
- 不把未标注甲方来源的 Codex 输入反推为客户需求，不把某客户决定复制给另一客户。
- 不用 workflow payload 补造事实。
- 不用前端本地派生替代后端事实 usecase。
- 不覆盖历史决定，不为需求管理提前创建泛化 ChangeUsecase、配置引擎或平行状态表。
