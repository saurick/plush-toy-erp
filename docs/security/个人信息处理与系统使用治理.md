# 个人信息处理与系统使用治理 / Privacy Notice And System Use Governance

## 结论

plush-toy-erp 是客户私有化部署的内部 ToB 系统，不设置公众注册、广告画像或“一勾全同意”。产品提供三层闭环：登录前和登录后都能查阅的个人信息处理规则、内部系统使用规则，以及登录账号对当前内容版本的“已阅读并知悉”审计回执。

知悉回执只证明告知已送达，不替代处理依据，也不替代依法需要的单独同意、书面同意、劳动人事规则、保密协议或客户与受托方之间的委托处理协议。

## 为什么内部 ToB 也需要

系统虽然不面向公众，但会处理管理员和员工的账号、手机号、岗位权限、操作日志，也可能承载客户、供应商、联系人和附件中的个人信息。内部使用场景不会自动排除个人信息保护、网络安全、劳动人事和合同义务。

当前设计主要对应以下要求：

- 处理前以显著、清晰方式告知处理者、联系方式、目的、方式、信息种类、保存期限和权利渠道；处理规则应公开且便于查阅和保存。
- 委托他人处理时，约定目的、期限、方式、信息种类、保护措施和双方权利义务，并监督受托活动。
- 保存期限遵循实现目的所必要的最短时间；网络运行和安全日志按适用要求至少保存六个月。
- 发生或可能发生泄露、篡改、丢失时及时补救，并依法评估通知个人和主管部门。

主要法律原文入口：

- [中华人民共和国个人信息保护法](https://www.cac.gov.cn/2021-08/20/c_1631050028355286.htm)
- [网络数据安全管理条例](https://app.www.gov.cn/govdata/gov/202409/30/520076/article.html)
- [中华人民共和国网络安全法（2025 年修正，2026 年 1 月 1 日起施行）](https://sdca.miit.gov.cn/zwgk/fgbz/art/2026/art_4815dd4ec11d454783b83a91502a3cc7.html)

## 产品实现合同

| 层次       | 当前实现                                                                              | 不代表什么                           |
| ---------- | ------------------------------------------------------------------------------------- | ------------------------------------ |
| 公开查阅   | `/legal/privacy` 与 `/legal/system-rules`，无需登录                                   | 不代表每项处理都基于同意             |
| 登录提示   | 登录页固定链接；短信模式在手机号旁提示用途和处理方入口                                | 不增加强制勾选或营销授权             |
| 登录后入口 | 电脑端账号菜单、手机端“我的 / 入口与安全”                                             | 前端入口不是后端权限边界             |
| 首次知悉   | 登录后按当前账号、规则版本和内容指纹核对；未命中时显示不可关闭的知悉提示              | 不是电子签名，也不是客户合同签署     |
| 变更重提示 | 产品正文 revision、客户主体、联系渠道、处理方、保存或跨境配置任一变化都会改变内容指纹 | 不能用旧回执覆盖新内容               |
| 审计证据   | 后端追加 `legal_notice_acknowledgement` 运行时审计事件                                | 不保存手机号、密码、token 或业务原文 |
| 故障边界   | 状态核对失败时显示持续警告和重试入口，不让隐私辅助接口拖垮全部 ERP                    | 不把失败状态伪装为已知悉             |

## 客户配置

每个客户的公开配置使用 `legalNotice`：

| 字段              | 作用                             | 更新条件                         |
| ----------------- | -------------------------------- | -------------------------------- |
| `noticeVersion`   | 人工可读版本                     | 正文、处理目的或重要口径变化     |
| `effectiveDate`   | 当前版本生效日期                 | 新版本启用                       |
| `controllerName`  | 个人信息处理者名称               | 客户法定主体变化                 |
| `contactChannel`  | 查阅、更正、删除、注销和投诉渠道 | 客户负责渠道变化                 |
| `storageLocation` | 主要部署和存储位置               | 目标部署地域或模式变化           |
| `crossBorderRule` | 跨境现状和触发程序               | 出现境外接收方或跨境访问         |
| `processors[]`    | 名称、目的、信息种类和触发条件   | 启用、替换或停用短信等外部处理方 |
| 三类 retention    | 账号、安全日志、业务审计保存口径 | 客户记录保存制度变化             |

Product Core 不硬编码 `yoyoosun`。中性默认只保证页面可读；正式交付必须由客户配置写出真实处理者和联系渠道。处理方未登记时，页面明确显示“当前未登记”，不能静默假设。

## 处理依据与同意边界

ToB 内部账号常见处理依据包括履行合同、依法制定的人力资源管理规则、法定义务和网络安全需要。只有具体可选处理确实以同意为依据时，才单独取得并提供撤回方式。

禁止使用以下误导性做法：

- 用“继续登录即同意全部条款”概括所有处理依据。
- 把隐私规则、保密制度、劳动管理、软件许可和客户合同塞进一个不可分割勾选框。
- 用前端本地存储充当正式知悉证据。
- 内容变更但沿用旧版本或旧指纹。
- 把页面入口、知悉回执或 super admin 身份解释为可以越权读取业务数据。

## 保存与删除边界

- 账号和授权信息保留至账号不再需要；停用用于临时暂停，正式注销终止后续登录。
- 注销不物理删除已过账、审批、财务、库存、质量或其他承担证明责任的业务记录。
- 网络运行和安全日志按适用要求至少保存六个月。
- 业务与审计记录保存至业务目的、法定义务或争议处理期限届满，再由部署单位按记录类别删除或匿名化。
- 当前产品没有把所有表统一套一个自动清理期限；客户必须按实际记录类型确认和执行 retention，不能让公开文案与运行事实相反。

## 处理方与委托关系

客户通常决定处理目的和方式，是个人信息处理者。软件实施、托管、短信、备份或运维方是否构成受托人，要按实际访问、指令和合同判断，不能只看产品名称。

启用外部服务前至少完成：

1. 确认必要性、数据最小化、部署地域和安全能力。
2. 在客户配置中登记实际名称、目的、信息种类和触发条件。
3. 使用[个人信息委托处理协议模板](个人信息委托处理协议模板.md)约定边界；涉及转委托须取得处理者同意。
4. 验证关闭功能后不再发送数据，并更新规则版本或内容指纹。

## 发布与验收

交付前逐项确认：

1. 登录页、公开页、电脑账号菜单和手机“我的”均可到达规则。
2. 处理者名称、联系渠道、存储位置、短信处理方和跨境口径与目标配置一致。
3. 新账号提示知悉；确认后写一条不含 PII 的审计；相同内容重放不重复写；内容变化重新提示。
4. 知悉接口失败只显示警告，不清理用户数据、不伪造已知悉，也不泄露原始错误。
5. 深色模式、手机窄屏、长主体名称、键盘焦点、公开无登录访问和退出路径可用。
6. 客户已确认 retention 和权利请求责任人；合同模板如需生效，已在受控合同系统签署，而不是把仓库模板当成签署证据。

本地代码和浏览器绿色只证明产品实现；是否已发布、目标配置是否一致、协议是否签署以及客户是否验收必须分别报告。
